## 1. Vision

**Groundly turns a folder of course materials into a study loop the student's own AI agent can run.** A student runs `groundly index ./slides/` once; from then on, any MCP-capable agent (Claude Code, Claude Desktop, Codex) can search the actual course content with page-level citations, map the course as a topic tree, quiz the student topic by topic through a question gate no ill-formed or ungrounded question can pass, and track what the student has mastered. The core loop: **index → search → topic tree → gated tests → progress.** The knowledge base is a file that can be shared with any other Groundly user and used directly.

Everything runs on the student's machine. There is no server, no account, no upload. **Groundly never asks for an API key**: it runs no LLM of its own, and the student's existing AI subscription (Claude Code, Claude Desktop, Codex) does the thinking.

**A learning session happens entirely in the student's host plus Groundly's local page.** Groundly does not export to other study apps; a feature that sends the student elsewhere to study is out of scope (decision 38). Two fixed chores, writing questions and grading written answers, can also be started from the page, which runs the student's own Claude Code headless for them; conversation stays in the host (decision 46).

**Why not NotebookLM or a Claude Project?** Three properties they don't have: (1) **gated generation** — no question the host generates is stored unless it is well formed and re-retrieval surfaces one of its cited chunks (the question gate, decision 44; it does not check that the answer key is right); the topic map already has a gate, which checks only that each topic is in the course (a topicality check, not a check that a summary is true); (2) **structural citations** — every chunk carries a `groundly://` URI resolving to document + page + heading path; (3) **a portable pre-built index** — one student pays the indexing cost, the whole course imports the result.

**Thesis-level contribution:** two measured comparisons on real, heterogeneous university course corpora (RO/EN mixed) — classic RAG vs GraphRAG retrieval quality, and enforced vs agent-mediated grounding — both complete; and the engineering result, a zero-key verified study loop (citations, verifier gate, quizzes, mastery) running on the student's existing AI subscription.

## 2. Users

One human role: the **student** (owner of the machine and the data). The other "users" are **agents** — MCP hosts acting on the student's behalf. There is no auth, no roles, no tenancy: subject scoping is filesystem layout, and privacy boundaries are file boundaries.

## 4. System Architecture

One Python package (`uv tool install groundly`), three runtime modes, zero services:

```
  Claude Code / Codex / Desktop        terminal (student)
        │ MCP (stdio, host-spawned)         │ one-shot verbs
        ▼                                   ▼
  ┌──────────────────── client layer ──────────────────────┐
  │ mcp/ FastMCP tools     cli/ typer verbs                │
  │ stdio: `groundly mcp`  (index/list/title/remove/drop/  │
  │ HTTP: `groundly mcp --http`  search/import/export/...) │
  │ web/ topic-tree and test page (`groundly serve`)       │
  └──────────────┬───────────────┬─────────────────────────┘
                 ▼               ▼
  ┌──────────────────── service layer ─────────────────────┐
  │ agents/    gates: verifier, topic tree (nothing       │
  │            unchecked is stored)                        │
  │ retrieval/ dense + sparse + BM25 → RRF → rerank        │
  │ ingestion/ docling subprocess → chunk → embed          │
  └──────────────┬──────────────────────────────────────────┘
                 ▼
  ┌────────── foundations ─────────────┐
  │ llm/  bge-m3 + reranker, in-process│  lazy-loaded; no LLM client
  │ core/ stores (SQLite WAL), manifest│
  └──────────────┬─────────────────────┘
                 ▼
  ~/.groundly/<SUBJECT>/
```

### Storage (`~/.groundly/`, global; `GROUNDLY_HOME` overrides)

```
~/.groundly/
  config.toml          # operational settings (no keys)
  <SUBJECT>/
    manifest.json      # format + model pins (the interchange contract)
    materials/         # original digital files (citation targets)
    store.db           # SQLite: chunks, vectors (sqlite-vec), sparse terms,
                       #         FTS5, the topic tree             → EXPORTED
    progress.db        # the student's private study state       → NEVER exported
```

The **privacy boundary is a file**: `store.db` travels, `progress.db` never does. Subject isolation is directory isolation — no query *can* cross subjects.

### Component decisions

| Component | Decision | Decisive reason |
|---|---|---|
| Distribution | Python package via `uv` | Docling ecosystem is Python-only |
| Interface | MCP server (FastMCP, stdio + HTTP) + CLI (typer) + a local page (Starlette, `groundly serve`); `groundly start` serves the page and HTTP MCP from one process (decision 45); **no TUI** | The host agent is the interactive surface; CLI verbs are batch lifecycle; the page shows the map and takes tests, writing only a submitted attempt to `progress.db` (decision 44), and its Write questions and Grade now buttons start the student's own Claude Code headless (decision 46) |
| Storage | SQLite (WAL) + sqlite-vec + FTS5, files on disk | Zero services; export = zip; exact KNN at subject scale |
| Extraction | Docling + bundled RapidOCR, one warm worker process per `index` run | Local/offline, zero-key; scanned course PDFs are common; the worker keeps per-file crash and timeout isolation without a process start per file (decision 48) |
| Embeddings | `bge-m3` local, pinned incl. hf_revision; dense + learned sparse; MLX on Apple Silicon (macOS 14+), torch elsewhere | RO/EN cross-lingual; the pin makes shared vectors compatible; the engine is not part of the pin and must stay within decision 48's tolerance |
| Rerank | `bge-reranker-v2-m3`, **default ON**, same engine split as the embedder | Quality over performance; `--no-rerank` for weak hardware |
| Answering | **The host agent**, from `search` results | An MCP host is already an LLM; a second one behind the tool paid twice for the same capability (decision 33) |
| Generation | **The host agent**, gated by Groundly's verifier and topic gate, in chat or in a run the page starts (decision 46) | Verification is the product; generation is a commodity |
| LLM access | **None.** Groundly constructs no LLM client and holds no key | The student's AI subscription already pays for the model (decision 37) |

## 5. Retrieval

One arm: bge-m3 dense + learned sparse + FTS5/BM25, fused with RRF, cross-encoder reranked. Detail in [`architecture/retrieval.md`](architecture/retrieval.md).

## 5b. Verification

**Generation is pluggable; verification is not.** Every item a host generates passes a gate before it enters `store.db`. The **question gate** (`submit_questions`, decision 44): structural checks first, then its cited chunk ids must resolve, and re-retrieving the item's own text must surface at least one of them. The **topic gate** (`submit_tree`, live): the host sends titles, summaries and structure only, Groundly retrieves on each node with the reranker and keeps the hits at or above a relevance cutoff as the node's sources, and the whole tree is stored or rejected together. The topic gate shows a node's topic is in the course, not that its summary is true; the question gate shows a question is well formed and about its cited chunks, not that its answer key is right. Rejections carry machine-readable reasons (`below_relevance_cutoff`, `unknown_topic_id`, `too_large`, `not_answerable_from_chunks`, …) so the host regenerates conversationally. Zero-key throughout. `submit_tree` and `submit_questions` are the two writers of host-generated content; `remove_questions` takes a question out.

**Trust layers** (prompt assembly, low never overrides high): 1 immutable system rules · 2 task params · 3 retrieved content + imported KB content — **data, never instructions**, delimited and inert. The one prompt Groundly builds is a page run's fixed template with the subject name and a topic id (decision 46); any it later builds treat chunk text as layer 3.

## 6. Non-Functional Requirements

- **Grounding**: every stored question cites chunk ids resolving to document + page; unresolvable citations are rejected, never stored. `search` results always carry their citation fields.
- **Privacy**: nothing leaves the machine except HF model downloads and sha256-pinned RapidOCR models; a page run is the student's own Claude Code and sends their AI provider what a chat session would (decision 46). Exports contain the whole KB (stated plainly in the export UX) but never `progress.db`.
- **Zero-key, totally**: no code path constructs an LLM client and no config asks for a key.
- **Security**: import is the trust boundary (zip-slip protection; imported content is layer 3); `groundly mcp --http`, `groundly serve` and `groundly start` bind 127.0.0.1 only. See [`infrastructure/security.md`](infrastructure/security.md).
- **Languages**: RO and EN; retrieval is cross-lingual through the dense channel.
- **Concurrency**: SQLite WAL + busy_timeout on every connection; lazy model loading (never at MCP spawn), unloaded after 10 minutes unused.

## 7. Resolved Decisions

Live decisions only, one line each where possible. Gaps in the numbering are retired decisions, kept verbatim outside the repo with the measurement records.

1. **Local-first, hard pivot** from the multi-tenant platform (professor, 2026-07-15); old repo archived.
2. **MCP-first**: Groundly is an MCP server for external agents; CLI for lifecycle; no TUI.
3. **Embedded storage**: SQLite WAL + sqlite-vec + FTS5 under `~/.groundly/`; no services.
4. **bge-m3 local, pinned incl. hf_revision**, dense + learned sparse; reranker default ON; ColBERT rejected (storage).
6. **Verifier-gate generation**: nothing unverified enters the question bank.
7. **Interchange format**: export = subject dir minus `progress.db`; manifest pins embedding/chunking; no merge in v1; import creates a fresh `progress.db`.
8. **Frameworks**: FastMCP (the tool surface) only. Starlette and uvicorn serve the topic-tree page (decision 41); they are not a second tool-surface framework.
11. **Pilot subjects: two** — apd (Parallel & Distributed Algorithms) and passc (Software Architecture).
12. **Timeline**: defense June/July 2027.
13. **Expanded ingest formats** (2026-07-16): all docling-native formats, notebooks (decision 43), and any other regular file that probes as plain text: no NUL bytes, and either UTF-8 or a legacy 8-bit encoding with no control bytes (read as UTF-8 with replacement characters), up to 10 MB. Deny-lists: noisy text (`.lock`, `.svg`, `.map`) and key or credential files (`.key`, `.pem`, `.env`, `id_rsa` and its siblings), which would otherwise ship in exports. Each skip names its cause.
14. **OCR enabled** (2026-07-17): docling's bundled RapidOCR is local, offline and zero-key; scanned course PDFs are common.
15. **Per-subject OCR language** (2026-07-17): `--ocr-lang` recorded in the manifest; changing it later requires re-indexing and is refused with a specific message.
16. **`.groundlyignore`** (2026-07-19): a built-in junk-dir deny-list plus an optional per-root ignore file.
17. **Standalone image ingestion** (2026-07-20): raster images index through the same IMAGE→OCR path, first frame only.
18. **Operational settings are user-configurable** (2026-07-20): `[ingestion]`/`[retrieval]` knobs whose defaults equal the former hardcoded constants.
19. **bge-m3 inference in fp16 + streamed per-document embedding** (2026-07-20), from a memray profile. On the MLX engine the forward runs in f16 with inputs packed up to 1,024 tokens per pass (decision 48).
31. **The tool surface is the retrieval trigger** (2026-08-16): server instructions state the norm, tool descriptions say which tool, and no tool is ranked above another server-wide. Measured: instructions ending with a clause preferring one tool took a host given only `search` to 4/48 questions retrieved; deleting that clause took it to 29/48 (Fisher p=8.3e-08).
33. **MCP-first, zero-key** (Paul, 2026-09-11): the enforced `ask` pipeline and thick generation are removed. The host composes answers from `search` and will write generated items through `submit_*` tools; the verifier is unchanged; `search` writes no traces. Measured basis: a host *told* to retrieve drew with enforced `ask` on answer support, and `ask` refused 28–47% of questions on a below-floor model. (Amended by decision 46: the page may start the host for two chores; Groundly still generates nothing.)
34. **The research surface is tagged and removed** (Paul, 2026-09-11): `eval/`, the eval verbs, the gold sets, the router and the adaptive stub live at tag `thesis-experiments-2026-09`. Re-running an experiment means checking out the tag.
36. **LlamaIndex dropped** (Paul, 2026-09-11): one retriever left, so the shared-interface reason is gone. A frozen `Hit` dataclass replaces `NodeWithScore`.
37. **GraphRAG dropped; Groundly runs no LLM** (Paul, 2026-10-30): the graph build, `export-graph`, the litellm provider path and all provider config are removed. GraphRAG was the last thing that needed a key, its setup was a hassle, and its flat co-occurrence communities never mapped a course the way students think about it; the host-built topic tree (sub-project 2) replaces it. A bundle that still carries `graph/` imports normally: the directory and the manifest's `graphrag` block are ignored, with no `format_version` bump.
38. **Flashcards dropped; the study loop stays in the host** (Paul, 2026-10-31): `submit_cards`, `list_decks`, `export_deck`, `groundly export-deck` and the genanki `.apkg` export are removed. Principle: a learning session happens entirely in the student's host plus Groundly's local page — an Anki export sent the student to another app whose review history never came back, and quizzes keep the verified-generation guarantee. The MCP surface is now four entries, and `get_page` takes the citation `uri` that `search` returns (the fragment survives as a tool argument; FastMCP drops it from resource reads, so the resource is always the whole document). With no users yet, `store.db` restarts as one schema at `user_version = 1` without the deck/question tables; quizzes design their own, and existing subjects and older bundles re-index (refused with that message). The rule that every stored item records its generation source goes with the old tables: since decision 33 every item is host-generated. Coding challenges move to Ideas. The release restarts at 1.0.0.
39. **Dependencies upgraded at the 1.0 restart** (Paul, 2026-10-31): sentence-transformers 6.2.0, FlagEmbedding 1.4.2, transformers 5.x, rapidocr 3.10.0, docling 2.115.0 — held below 2.116, whose per-region OCR reorders words within a line ([`tech-stack.md`](tech-stack/tech-stack.md)). Measured: bge-m3 dense and sparse outputs and reranker scores are bit-identical to the old stack, so the embedding pin and manifest are unchanged; extracted chunk text may differ, which decision 38's re-index already covers.
40. **CLI and MCP surface made hard to misuse** (Paul, 2026-10-31): `init` is gone — `index` creates the subject, after checking every path exists so a typo leaves nothing behind. `remove` takes one or more materials and resolves them all before deleting; `drop` is the only verb that deletes a subject (an optional argument used to decide between deleting one file and the whole subject, `progress.db` included). `serve` is removed and reserved for the topic-tree page; MCP over HTTP is `groundly mcp --http`, still loopback-only with DNS-rebinding protection — two processes, two model loads if both run, accepted (amended by decision 45: `groundly start`). `-y/--yes` is the one prompt skip (`--force` survives only on `models install`). `retrieval.context_k` is renamed `retrieval.top_k` with no migration (an old key is ignored). Also: `index --retry-failed`, richer `list`, bare `groundly models` shows cache status and `uninstall` removes both models, plain-language `config set` errors that accept `none`. CLI `search -m` scopes every channel to one material; the dense channel scans that material's vectors because vec0 takes no material predicate without a schema change. The MCP `material` filter and any material listing wait for sub-project 2's outline tool, so a host never guesses filenames; the MCP surface is unchanged. Why now: no users, so renames are free, and `serve` had to be free before sub-project 2.
41. **Topic tree: host-built, Groundly-checked, read-only** (Paul, 2026-11-01). Shape: the host reads `outline(subject)`, writes a two-level tree of titles, summaries and structure, and sends it to `submit_tree`; `groundly skill install` puts the instructions for that in Claude Code, and `groundly serve [--port N]` (default 8765, 127.0.0.1 only) shows the result. The MCP surface goes from four entries to six (five tools plus the document resource). Choices and reasons:
    - *Read-only for this release.* Progress only means something once quizzes (sub-project 3) record answers, so the tree ships as a map alone: no progress tables, every node reads "Not started", no quiz button or deep links.
    - *A skill, not a server prompt.* Building the tree is the host model's work, as the second half of graphify is; Groundly cannot and will not call an LLM (decision 37). `SKILL.md` carries the instructions (amended by decision 47: one skill per flow, `groundly-map` for this one), which keeps the server's `instructions` a norm for the whole surface (decision 31), installed via `groundly skill install` to `~/.agents/skills/` and any present host among `~/.claude/skills/`, `~/.codex/skills/` and `~/.gemini/config/skills/` (Antigravity).
    - *Groundly chooses the sources.* The host supplies title and summary and gets no say over citations: Groundly retrieves on `title + "\n" + summary` with the reranker always on and keeps up to 5 hits at or above `TOPIC_RELEVANCE_CUTOFF = 1.0`. A source therefore cannot be invented or be a real-but-wrong slide, and the host never handles chunk ids. A probe showed the reranker scores separate on-topic from off-topic nodes well enough for a cutoff. The alternative, the host citing chunks and search confirming them, was rejected because it lets a host cite a real but wrong slide.
    - *Cutoff 1.0* held on host-written trees for apd and `passc`; the constant is the one thing to change if good nodes are rejected.
    - *Topicality only.* The gate shows a course passage is about the node's topic. It does not show the summary is correct, and no UI, doc or tool description may call a summary verified.
    - *Tables in schema v1, no migration.* `topics` and `topic_citations` join the single schema at `user_version = 1`: the project had just reset to v1 and subjects get re-indexed anyway. `AUTOINCREMENT` on `chunks.id` and `topics.id` means a deleted chunk's id is never reused, so a citation cannot silently point at a different chunk, and topic ids survive re-runs. Subjects indexed before the tables exist work for search and are re-indexed once; a bundle without the tables is refused on import, as is one whose tree is damaged.
    - *Consequences.* MCP tools now write `store.db` through the gate, so `ingestion` is no longer the only writer. `serve` adds a local page to the threat model ([`infrastructure/security.md`](infrastructure/security.md)). Starlette and uvicorn become direct dependencies; FastMCP already installed both, so the install does not grow, and they are not a second tool-surface framework. `serve` supersedes decision 40's reservation of the verb; the outline tool is the material listing decision 40 deferred, while the MCP `material` filter on `search` stays out.

42. **A subject's title is a label, not its name** (Paul, 2026-11-03): `groundly title <subject> <text>` stores an optional `manifest.title`, shown by `groundly list`, `list_subjects` and the topic-tree page. The subject name stays the one ID in commands, paths and `groundly://` URIs, and keeps its strict character set. Why: course names have spaces and diacritics ("Algoritmi Paraleli și Distribuiți"), but the name is a directory, an MCP identifier and a URI part, and a bundle can supply it, so loosening its check to allow them would weaken the import boundary and changing it would break citations already handed out. A label needs neither. Rejected: renaming to a long slug (breaks citations, long to type) and spaces in names (touches URIs and routes). Consequences: at most 120 visible characters, checked on every manifest read; titles from bundles are layer 3; a corrupt manifest costs `list_subjects` and the page only that subject's title, while `groundly list` still warns and skips the subject. No `format_version` bump: an older groundly ignores the field, and drops it if it rewrites the manifest.
43. **Notebooks are indexed; plain text stays verbatim** (Paul, 2026-11-03): an `.ipynb` is rendered to Markdown from its cells and chunked by docling, so its headings reach `heading_path` and `outline`, and its code stays intact. Saved outputs are dropped: they are machine-generated, and one embedded image would become hundreds of junk chunks. Plain-text chunks are cut from the source by tokenizer offsets, because decoding tokens collapsed all whitespace and broke the verbatim rule. The embedding pin, manifest and `format_version` are unchanged; a material already indexed keeps its old chunks until `groundly remove` and `groundly index` run on it.
44. **Tests are taken on the local page** (Paul, 2026-11-16; design in [`superpowers/specs/2026-11-16-tests-on-the-page-design.md`](superpowers/specs/2026-11-16-tests-on-the-page-design.md)). The host writes questions and `submit_questions` stores those that pass the question gate; the student takes a test drawn from that bank on the `groundly serve` page, one question per screen with feedback at the end. Groundly grades single-answer and multiple-answer questions at Submit, and the host reviews open answers afterwards through `review_answers`. Choices and reasons:
    - *The page, not the chat.* A test is sat with the feedback held back until the end, and the page is the same in every host. The planned chat tools `quiz` and `record_answer` are dropped. A host-drawn artifact was rejected: it cannot write `progress.db`, Claude Code has none, and it would put model-written HTML in front of the student.
    - *The page writes `progress.db` and nothing else (amended by decision 46: it also starts the host for two chores, and still writes no rows to `store.db`).* One request at Submit grades and saves the whole attempt in one transaction; a test abandoned before Submit records nothing. The write route requires the page's own `Origin` and a JSON body on top of the Host check. This supersedes decision 41's "read-only"; the page still writes no rows to `store.db` and loads no model.
    - *The host reviews open answers.* Self-marking was rejected: it is a flashcard (decision 38) and would feed a self-reported mark into mastery.
    - *A test is drawn from the bank at start*, for a subtopic, a big topic or the whole course. Fixed tests written by the host can be added on top later.
    - *The gate shows form and topicality, not a correct key.* It checks structure, that cited chunk ids resolve, and that re-retrieving the question's own text finds one of them. Proving a key right needs a model Groundly does not have, so nothing may call a key verified; the result screen shows the cited page beside every answer and `remove_questions` takes a wrong question out.
    - *One additive schema upgrade.* `store.db` goes from `user_version` 1 to 2 by creating the empty question tables on open. This departs from decision 41's no-migration stance because dropping and re-indexing a subject would also delete its reviewed map.
    - *A re-map never destroys questions silently.* `submit_tree` rejects a tree that drops or subdivides a topic holding questions (`topic_has_questions`).
    - *Consequences.* The MCP surface goes from six entries to ten (`submit_questions`, `remove_questions`, `review_answers`, `progress`). The question gate is a third writer to `store.db`. The bank lives in `store.db` and travels in bundles; attempts and answers live in `progress.db` and never do. Live coding stays refused at the door.
45. **`groundly start`: the page and HTTP MCP on one address** (Paul, 2026-11-17; design in [`superpowers/specs/2026-11-17-groundly-start-design.md`](superpowers/specs/2026-11-17-groundly-start-design.md)). `groundly start [--port N]` (default 8765, 127.0.0.1 only) runs one process serving the page at `/` and the MCP tools over Streamable HTTP at `/mcp`; the CLI mounts FastMCP's HTTP app after the page's routes, with FastMCP's own Host/Origin guard left on. Why: several Claude Code sessions often work on different subjects at once, and over stdio each spawns its own Groundly and loads bge-m3 and the reranker separately; one HTTP process loads them once, and one command replaces two processes on two ports. This amends decision 40's "two processes, two model loads if both run, accepted". The page and `/mcp` answer to the fixed names `127.0.0.1`, `localhost` and `groundly.localhost` (never configurable: the list is the DNS-rebinding guard); browsers resolve `*.localhost` to loopback themselves, and the printed `127.0.0.1` page URL covers any that do not. The printed MCP URL and connect command use `127.0.0.1`: an MCP client resolves through the OS, and a resolver that forwards `*.localhost` upstream could point it at another machine. `serve` (page only, now opening `groundly.localhost`) and `mcp --http` (8000) are unchanged. Rejected: a port-free URL (port 80 on loopback needs root, or a privileged proxy that would also take over the Host/Origin decision) and a `.local` name (mDNS: Bonjour collisions and lookup stalls). The page's own routes still load no model; in the `start` process the first `/mcp` search does.
46. **The page starts the student's own host for two chores** (Paul, 2026-11-17; design in [`superpowers/specs/2026-11-17-page-chores-design.md`](superpowers/specs/2026-11-17-page-chores-design.md)). A **Write questions** button in a topic's panel, and **Grade now** on a result awaiting review, start the student's own Claude Code headless (`claude -p`) from the page process. One click on a subtopic brings it to 10 questions; one click on a big topic brings each of its subtopics below 10 up to 10; one grade run reviews every written answer in the subject awaiting review. The page shows the run's steps (from tool names and counts only), a **Stop** button, then the run's summary as text, and re-reads the map or result. Why: the study loop crossed between page and chat by phrases the student had to remember, and chat cannot fill a course with questions (apd: 14 big topics, 66 subtopics, 10 questions on one). Writing and grading are fixed procedures whose output passes a gate into tables the page already reads; explaining and mapping need a conversation and stay in the host. **Isolated:** `--strict-mcp-config` with Groundly only (`/mcp` on the same port under `start`, the same installation's `groundly mcp` under `serve`), `--setting-sources ""` (no hooks, plugins, CLAUDE.md), `--tools ""` (no files, shell or web), a per-flow `--allowedTools` (write: `list_subjects`, `progress`, `search`, `get_page`, `submit_questions`, and `topic` since decision 47; grade: `review_answers`, `get_page`), `--permission-mode dontAsk`, the packaged `SKILL.md` through `--append-system-prompt-file` (amended by decision 47: the flow's own skill), no session persistence, an argv list with no shell, one fixed run directory under Groundly's home. The init event is checked fail-closed: any tool not prefixed `mcp__groundly__`, or any server but a connected `groundly`, kills the run before its first turn (`isolation_failed`). **Still no key and no client (decision 37):** the run is the student's binary on the student's login, its environment inherited; Groundly passes no credential and no `--model`, so Claude Code's built-in default is used, and `ANTHROPIC_MODEL` set when starting Groundly is the student's way to a cheaper one. The prompt is a fixed template filled with the subject name and a topic id only, never layer-3 text. This is the change to decision 33's "no generation loop inside Groundly": Groundly still generates nothing, but it now starts the host that does, and every write still passes `submit_questions` or `review_answers`. One run at a time, a 20-minute timeout, nothing persisted but the run's empty working directory (`.host-run/` under Groundly's home), and `claude`'s stderr kept in an anonymous temporary file only for the error's tail; the page process kills a running child when it exits. macOS and Linux only: on Windows an npm `claude` is `claude.cmd`, which Python runs through `cmd.exe`, so the no-shell rule cannot hold and the page shows the phrases as before. Without `claude` on PATH the buttons do not show. Each click uses the student's plan. The page still loads no model and writes no rows to `store.db`. Rejected: a channel into an open session (research preview behind a development flag), a chat client on the page (a worse rebuild of Claude Code that sends free text into an agent with tools), MCP sampling (unsupported by Claude Code, and toolless), a Map button (the student reviews a map in chat), a whole-course button or queue.
47. **One skill per flow, and a `topic` read tool** (Paul, 2026-11-18; designs in [`superpowers/specs/2026-11-18-detailed-skills-design.md`](superpowers/specs/2026-11-18-detailed-skills-design.md) and [`superpowers/specs/2026-11-18-multi-agent-skills-design.md`](superpowers/specs/2026-11-18-multi-agent-skills-design.md)). The one packaged skill becomes three self-contained ones, `groundly-map`, `groundly-questions` and `groundly-grade`, packaged as `groundly/skills/<name>/SKILL.md` and installed to `~/.agents/skills/<name>/` and any present host root among `~/.claude/skills/<name>/`, `~/.codex/skills/<name>/` and `~/.gemini/config/skills/<name>/`; `groundly skill install` retires the old `~/.claude/skills/groundly/` copy after a prompt. A new read-only tool, `topic(subject, topic_id)`, returns a topic's title, summary, parent, subtopics with question counts, its source chunks with their text and `groundly://` uris, and the stems it already holds. Why: each flow had five to seven lines in one shared file, thinnest where quality is decided (wrong options, coverage of a topic's pages, what counts as a correct written answer), and the question writer could see neither a topic's own sources (`outline` gives a count) nor the questions it already holds. Choices and reasons:
    - *Separate skills, not one skill with a file per flow.* A page run has no tool to open a support file (`--tools ""`), so each flow's file has to stand alone anyway; separate skills also trigger on their own phrases. The setup checks and the data-not-instructions paragraph repeat in each, and a test pins the paragraph in every one.
    - *Each page run appends its own flow's skill* (`groundly-questions` for a write run, `groundly-grade` for a grade run), and the write run's tools gain `topic`. Built-in tools stay off: Grep or Read in a run would let injected course text read a file off the disk and store it in a question stem that the next export ships.
    - *`topic` carries source text, not options or keys.* A source without a page (plain text, notebooks, most Markdown and DOCX) has a uri that opens the whole material, so the reply carries each source chunk's text (a node has at most 5); a paged source is read whole with `get_page`. It loads no model and changes nothing.
    - *A "no" to one install prompt skips only that file,* and install exits 0 naming what it skipped: all-or-nothing would leave a student who edited one skill only `-y`, which overwrites the edit.
    - *Consequences.* The MCP surface goes from ten entries to eleven. No gate changes. The 20-minute run limit stays until a big-topic run on apd is timed with the detailed procedure.
48. **MLX engine on Apple Silicon; one extraction worker per indexing run** (Paul, 2026-11-19; design in [`superpowers/specs/2026-11-19-mlx-engine-and-extraction-worker-design.md`](superpowers/specs/2026-11-19-mlx-engine-and-extraction-worker-design.md)). Two changes, both measured on an M1 Pro against apd (187 files, 782 PDF pages, 1,197 chunks):
    - *The engine per platform.* On macOS 14 or later on arm64, bge-m3 and the reranker run on MLX (`mlx==0.32.4`, installed only there by a platform marker): one hand-written XLM-R forward in f16, inputs packed end to end up to 1,024 tokens per pass, truncated as FlagEmbedding truncates (512 tokens for bge-m3; for the reranker the query cut to 384, then the passage to fit 512). Everywhere else, and on any Mac where `mlx` does not import, FlagEmbedding on torch runs unchanged. No setting chooses: zero-config stays total. The pinned bge-m3 weights ship as torch pickles, so they are converted once to f16 safetensors in a child process and kept under `~/.groundly/models/`; the serving process only reads safetensors, so `start`, `mcp` and `serve` never import torch on Apple Silicon. Measured, MLX against torch: bge-m3 over all 1,197 chunks 47.8 s against 69.9 s, model load 1.1–1.4 s against 7.7–9.2 s; reranking the 50 workload searches' pools 34.2 s against 59.4 s; `search` p50 708 ms against 1,272–1,276 ms; the topic gate 64 / 37 / 80 s against 108 / 63 / 127 s on apd, bgf and sma.
    - *The pin is unchanged; the measured tolerance is the contract.* Model, revision, dim, dtype and normalization stay as they are: no manifest bump, no re-index, and bundles move between a Mac and a Linux machine as before. An engine must stay within what MLX measured against torch on every apd chunk and the 50 workload pools: dense cosine ≥ 0.9997 (minimum 0.99978); sparse top-10 identical up to f16 near-ties (1,196 of 1,197 chunks within 1e-3 of the 10th weight, the last at 1.1e-3; 1,168 with the identical token set); rerank top-5 identical as a set on all 50 pools, in identical order on 48, the two swaps adjacent ranks 4 and 5 whose torch scores lie 0.002 and 0.005 apart; maximum rerank score difference 0.026 (0.034 on full 512-token inputs), f16 against torch's fp32 reranker. Rejected: an `engine` field in the pin, which would make every Mac↔Linux import re-embed.
    - *The topic gate's flips are accepted.* `submit_tree` compares raw reranker scores to `TOPIC_RELEVANCE_CUTOFF`, so a hit at the cutoff can land on the other side on a Mac. Measured over the apd, bgf and sma trees (80 + 46 + 79 nodes): no node changes accept or reject; 2 apd nodes change their source set (one swaps its fifth source, one loses a third source scored at the cutoff). That is accepted: the gate shows topicality only, and the closest node's top score sits 0.17 from the cutoff.
    - *One warm extraction worker per run.* `groundly index` starts one docling worker on the first file that needs one and sends it every file over a line protocol; each file keeps its own output file, its own `ingestion.timeout_seconds` and today's failure messages: a crash (`parser failed: …`), a timeout (`extraction timed out after Ns`), a file over `ingestion.max_file_size_mb` (`file too large — …`, refused before it reaches the worker) and a file with no text (`no readable text — OCR found nothing to extract`) each end `extraction_failed`, and the next file indexes. A crash fails only the file in flight and a fresh worker takes the next file; a timeout kills and restarts the worker. The worker never outlives the run. Measured: `groundly index` of apd took 4.2 min (252 s, model caches warm, 1,197 chunks), where the per-file process took 21.6 min, about 15 of them process start and model reload.
    - *Rejected, with the spike's numbers.* Torch-free extraction (docling's ONNX layout model): three patches to docling internals and a `--no-deps` install that `uv tool install` cannot express, PDFs ~1.2× slower (142.6–156.2 s against 116–123 s on 782 pages), no TableFormer (table-heavy decks down to word F1 0.84); torch stays installed for the worker. Apple Vision OCR: inside docling the layout model sets the page time (27.5 against 30.6 s on 30 pages), worse on English slides (F1 0.917 against 0.951) and on Romanian diacritic words (0.957 against 0.971), and unpinned; RapidOCR stays (decision 14). This supersedes decision 19's "fp16" only for the MLX path; the torch path is unchanged.
