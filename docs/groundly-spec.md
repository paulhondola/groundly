## 1. Vision

**Groundly turns a folder of course materials into a portable, agent-consumable knowledge base.** A student runs `groundly index ./slides/` once; from then on, any MCP-capable agent (Claude Code, Claude Desktop, Codex) can answer questions grounded in the actual course content with page-level citations, generate execution-verified tests and flashcards, quiz weak areas, and track mastery. The knowledge base — vectors, graph, verified decks — is a file that can be shared with any other Groundly user and used directly.

Everything runs on the student's machine. There is no server, no account, no upload. The only external dependency is an optional OpenAI-compatible LLM endpoint (the student's own cloud key, or LM Studio/Ollama).

**Why not NotebookLM or a Claude Project?** Four properties they don't have: (1) **verified generation** — every generated question passes a server-side verifier, including subprocess *execution* of code answers; (2) **page-level citations** enforced structurally, with "not covered by the course materials" instead of hallucination; (3) **a portable pre-built index** — one student pays the indexing cost, the whole course imports the result; (4) **cross-host progress** — mastery and study memory persist across whatever agent the student talks to.

**Thesis-level contribution:** (a) an empirical comparison of classic RAG vs GraphRAG retrieval quality on real, heterogeneous university course corpora (RO/EN mixed), stratified by query class, across four retrieval arms; (b) a measured comparison of **enforced vs agent-mediated grounding** (the `ask` tool's pipeline vs host-composed answers over `search`); (c) a portable knowledge-base interchange format with pinned-model compatibility semantics.

## 2. Users

One human role: the **student** (owner of the machine and the data). The other "users" are **agents** — MCP hosts acting on the student's behalf. There is no auth, no roles, no tenancy: subject scoping is filesystem layout, and privacy boundaries are file boundaries (see §4).

### Storage (`~/.groundly/`, global; `GROUNDLY_HOME` overrides)

```
~/.groundly/
  config.toml          # provider config per call class + operational settings (decision 18)
  <SUBJECT>/           # e.g. PDSS/ — one dir per subject
    manifest.json      # format + model pins (the interchange contract)
    materials/         # original digital files (citation targets)
    store.db           # SQLite: chunks, vectors (sqlite-vec), sparse terms,
                       #         FTS5, verified decks/questions  → EXPORTED
    progress.db        # quiz history, study notes, traces       → NEVER exported
    graph/             # MS graphrag parquet artifacts
```

The **privacy boundary is a file**: `store.db` travels, `progress.db` (your queries, results, notes) never does. Subject isolation is directory isolation — no query *can* cross subjects.

### Component decisions

| Component | Decision | Decisive reason |
|---|---|---|
| Distribution | Python package via `uv` | Docling/LlamaIndex/graphrag/RAGAS ecosystem is Python-only |
| Interface | CLI (typer) + MCP server (FastMCP, stdio + HTTP); **no TUI** | The host agent is the interactive surface; residual tasks are batch verbs |
| Storage | SQLite (WAL) + sqlite-vec + FTS5, files on disk | Zero services; export = zip; exact KNN at subject scale |
| Extraction | Docling + bundled RapidOCR OCR | Pivot #3 reversed (2026-07-17): OCR ships in base docling, local/offline, zero-key; scanned course PDFs are common. Standalone raster images index via the same IMAGE→OCR path (decision 17) |
| Embeddings | `bge-m3` local, pinned incl. hf_revision; dense + learned sparse | Quality-first (Paul); RO/EN cross-lingual; the pin makes shared vectors compatible |
| Rerank | `bge-reranker-v2-m3`, **default ON** | Quality over performance (Paul); `--no-rerank` for weak hardware |
| Graph | MS `graphrag` per-subject batch → parquet | Canonical GraphRAG; naturally file-based |
| Retrieval orchestration | LlamaIndex `Retriever` interface | One interface across four evaluation arms |
| Agent loops | **Plain async functions** (LangGraph dropped) | Post-pivot roster is a pipeline + two bounded loops |
| LLM access | OpenAI-compatible `base_url` + key per call class (`chat`, `generation`, `extraction`, `router`, `judge`) | One code path for cloud keys and LM Studio/Ollama; no subscription-OAuth piggybacking |
| Flashcard delivery | `.apkg` export via genanki | Anki owns daily review; Groundly owns verified generation |
| Dashboard | One static HTML page served by `groundly serve` | React toolchain for one page was unjustifiable |

## 5. Hybrid Retrieval Strategy

Four arms behind one LlamaIndex `Retriever` interface — see [`architecture/retrieval.md`](architecture/retrieval.md):

1. **Vector baseline** — three channels: bge-m3 dense (exact KNN via sqlite-vec) + bge-m3 learned sparse + FTS5/BM25, fused with RRF, cross-encoder reranked.
2. **GraphRAG** — graphrag local search (entity-anchored, multi-hop) and global search (community summaries, synthesis).
3. **Static hybrid** — graph local search fused with the baseline; rerank. (The router that once dispatched into it came off the ask path at decision 28 and stayed off at 29.)
4. **Adaptive agentic** — retrieve → self-grade → escalate/rewrite, hard-bounded at 2 iterations. **Declared, not implemented** — `build=None` in `ARM_TABLE`.

Arms 1–3 are all selectable via `ask(arm=)` / `groundly ask --arm` and scoreable via `groundly eval --arms`; `vector` is the default because it won the measured comparison, and `graph-global` is scoreable but not askable because it returns no relevance order (decisions 28 and 29).

**Evaluation plan (thesis core):** gold Q/A set per pilot subject from past exams, stratified factoid / multi-hop / global-synthesis, RO and EN, cross-lingual queries as their own slice. Metrics per arm × class: retrieval hit rate, RAGAS groundedness/faithfulness, citation accuracy, router accuracy, cost, latency. Plus the **grounding-fidelity experiment**: the same gold questions answered via the enforced `ask` pipeline vs host-composed over `search`. GraphRAG is timeboxed; "the graph didn't help" is a valid, publishable finding. **Gold-set construction starts before implementation** — it needs the professor, not code.

## 5b. Agent Layer

Governing rule: agents only where the system must decide, iterate, or use tools mid-task — everything else is a pipeline. See [`architecture/agents.md`](architecture/agents.md). Roster of two:

1. **Ask pipeline** (interactive): retrieval through the caller's arm (default `vector`, no router — decisions 28 and 29) → trust-layered prompt → generation → citation resolution → cited answer or "not covered". Exposed as the MCP `ask` tool and the `groundly ask` CLI verb — the same function is the product tool and the evaluation instrument. Only the CLI exposes `--arm`.
2. **Exam verifier** (the identity of generation): every question entering `store.db` passes verification — answerable from cited chunks (re-retrieval), answer key correct, distractors wrong, code executed in a subprocess with timeout. Generators are pluggable: **thick** (`generate_*`, Groundly's provider key) or **thin** (`submit_*`, the host agent generates, same verifier gates). Rejections carry machine-readable reasons so hosts regenerate conversationally.

**Trust layers** (prompt assembly, low never overrides high): 1 immutable system rules · 2 subject profile (user-editable, shippable in exports; trusted content never trusted authority, size-capped, cannot disable grounding) · 3 task params · 4 retrieved content + imported KB content + user input — **data, never instructions**, delimited and inert.

## 6. Non-Functional Requirements

- **Grounding**: every answer/question cites chunk ids resolving to document + page; zero resolvable citations = error; insufficient context = "not covered". No model-knowledge fallback on any path.
- **Privacy**: nothing leaves the machine except LLM calls to the student's own configured provider. Exports contain the whole KB (documented plainly in the export UX) but never `progress.db`.
- **Security**: import is the trust boundary (zip-slip protection; imported content is layer-4); subprocess runner (timeout + tempdir); `serve` binds 127.0.0.1 only. See [`infrastructure/security.md`](infrastructure/security.md).
- **Languages**: RO and EN; retrieval must be cross-lingual (RO question over EN slides — dense channel carries this; lexical channels are same-language).
- **Concurrency**: SQLite WAL + busy_timeout from day one (one-shot CLI and host-spawned MCP share `store.db`); lazy model loading (no 2.2GB load at MCP spawn); generation jobs serialized when the provider is a local runtime.

## 7. Resolved Decisions

One-line register:

1. **Local-first, hard pivot** from the multi-tenant platform (professor, 2026-07-15); old repo archived.
2. **MCP-first**: Groundly is an MCP server for external agents; CLI for lifecycle; no TUI (professor).
3. **Embedded storage**: SQLite WAL + sqlite-vec + FTS5 + parquet under `~/.groundly/`; no Postgres/Redis/Celery/Docker.
4. **bge-m3 local, pinned (incl. hf_revision)**, dense + learned sparse; reranker default ON; ColBERT rejected (storage). Quality over performance (Paul).
5. **No OCR** (professor, pivot #3) — digital documents only; vision fallback and photo notes dropped. **OCR portion reversed 2026-07-17** — see decision 14; standalone raster images now index via the same OCR path (decision 17, 2026-07-20). Vision fallback (VLM description) remains dropped; handwriting is out of reach (RapidOCR is print OCR).
6. **Verifier-gate generation**: server-side verifier mandatory; generators pluggable (thick/thin). Flashcards delivered as Anki `.apkg`.
7. **Interchange format**: export = subject dir minus `progress.db`; manifest pins embedding/graphrag/chunking; no merge in v1; import creates fresh `progress.db`.
8. **Frameworks**: LlamaIndex + MS graphrag + FastMCP, one owner each; **LangGraph and LangSmith dropped** — traces live in a local table.
9. **Providers**: OpenAI-compatible per call class; no subscription-OAuth piggybacking (ToS-fragile).
10. **Study memory**: `recent_activity` daily rollups + `remember` notes + `continue-studying` MCP prompt; no server-side LLM summarization.
11. **Pilot subjects: two** (Parallel & Distributed Algorithms; an ML course) — carried over from v1. Professor available for gold-set spot-checks.
12. **Timeline**: defense June/July 2027.
13. **Expanded ingest formats** (2026-07-16): all docling-native text formats (HTML, LaTeX, AsciiDoc, CSV, XLSX, EPUB) plus a wider plain-text set (rst, json, yaml, toml, sh, sql, cs, rb, kt, swift); `.ipynb` still excluded.
14. **Pivot #3 reversed — OCR enabled** (Paul, 2026-07-17): decision 5's "no OCR extras" premise was false — `docling==2.113.0` resolves to `docling-slim[standard]`, whose `standard` extra bundles RapidOCR (PP-OCR ONNX models) inside the wheel, local/offline, zero-key; scanned course PDFs are common enough to matter. `_extract_docling` now builds the converter with explicit `PdfPipelineOptions(do_ocr=True)` and the engine pinned to `RapidOcrOptions(backend="onnxruntime")`, default langs — docling's "auto" selection would silently switch engines (ocrmac; easyocr, which downloads models at runtime) if one ever appeared in the environment, and non-default langs are supported per subject (decision 15). The local/offline claim holds exactly for this pinned path. Consequences: `rapidocr==3.9.1` pinned exactly as a direct dependency; the PDF extraction-failure message changes to "no readable text — OCR found nothing to extract"; no re-index migration (DoclingDocument output and embeddings are unchanged by this pipeline-options change); OCR'd text becomes citation-target chunks like any other — citation accuracy on scanned sources is now bounded by OCR quality, not just layout parsing.
15. **Per-subject OCR language** (Paul, 2026-07-17): `groundly index --ocr-lang <code>` (e.g. `ro`) is recorded once per subject in `manifest.json`'s `ocr.lang` and passed to RapidOCR as `Rec.lang_type` via docling's `rapidocr_params` pass-through — docling's own lang mapping collapses ISO codes to the PP-OCRv4-era "latin" group, which rapidocr 3.9's default PP-OCRv6 multilingual rec model rejects while accepting the ISO code directly. On the pinned onnxruntime path the PP-OCRv6 multilingual models ship in the rapidocr wheel, so `--ocr-lang ro` stays fully offline (verified: no download on first use); a lang/backend combo resolving to a non-bundled model is fetched sha256-pinned from modelscope.cn (version-tagged under the `rapidocr==3.9.1` pin) inside the already-wrapped `initialize_pipeline()` step — a fetch failure is `EXIT_MODEL_UNAVAILABLE` like any other model load. Changing a subject's recorded lang is a re-index migration — refused at index time with a specific message while indexed materials exist (with none, e.g. after a mistyped code that fails every extraction, the lang may be corrected freely). Manifest change is additive-with-defaults (`ocr: {engine, lang: []}`), so `format_version` stays 1.
16. **`.groundlyignore`** (Paul, 2026-07-19): `groundly index` prunes a built-in junk-dir deny-list (`.git`, `.venv`, `venv`, `node_modules`, `dist`, `build`, `__pycache__`, `target`, `.idea`, `.vscode`) plus hidden dirs/files by default, and reads an optional `.groundlyignore` (one fnmatch pattern per line) at the root of each indexed directory — stdlib only, no `pathspec` dependency; full gitignore semantics (negation, anchoring, `**`) out of scope until needed. Explicit paths on the CLI are never ignore-filtered.
17. **Standalone image ingestion** (Paul, 2026-07-20): raster images (`.png .jpg .jpeg .tif .tiff .bmp .webp`) index as first-class inputs. docling routes `InputFormat.IMAGE` through the same `StandardPdfPipeline` as PDFs, so a single-frame image is treated as a one-page scanned PDF — OCR'd on the identical pinned `RapidOcrOptions(backend="onnxruntime")` path (decision 14), page-1 attribution, `--ocr-lang` applies unchanged (decision 15). `_extract_docling` registers the IMAGE format with the same `PdfPipelineOptions` used for PDF; **this registration is load-bearing** — without it docling's *auto* OCR selection would pick a different engine than the decision-14 pin (ocrmac on macOS, easyocr elsewhere with runtime downloads), silently diverging OCR output from the pinned interchange path. **Multi-frame rasters (multi-page TIFF, animated WEBP) index frame 0 only** (`_first_frame` flattens them): docling would otherwise expand them to N pages that `HybridChunker(merge_peers=True)` collapses into a single chunk carrying only the first page number — a citation that resolves to the wrong page. Multi-page scans belong in a PDF. OCR-only: no VLM captioning/description (that would require a provider, breaking zero-key indexing). A **title-only image** (or PDF page) parses to a heading-only doc that HybridChunker drops; `_extract_docling` salvages that text as one chunk rather than reporting "no readable text", so the OCR'd title still indexes. Image inputs are pixel-capped (`MAX_IMAGE_PIXELS`, ~100 MP) before decode — a specific `EXIT_INPUT_TOO_LARGE` failure — to bound decompression-bomb memory on the new attacker surface (security.md). Consequences: partial reversal of descope #5 — printed/typeset "photo notes" now index (handwriting and vision fallback remain out); a genuinely text-free image gets "no readable text — OCR found nothing to extract"; **no interchange change** — manifest and `format_version` unchanged, embeddings/graph identical, so no re-index migration; citation accuracy on image sources is bounded by OCR quality. Audio and XML docling formats remain out of scope (add when needed). Known limitation, not image-specific: the cross-page `merge_peers` collapse above also mis-attributes chunks that span pages in a **scanned multi-page PDF** (heading-less OCR text) — a pre-existing decision-14 weakness to fix in chunk page assignment separately.
18. **Operational settings are user-configurable** (Paul, 2026-07-20): `config.toml` grows beyond providers (decision 9). New `[ingestion]` / `[llm]` / `[retrieval]` tables expose tunable knobs whose **defaults equal the former hardcoded constants**, so zero-config behavior is unchanged: `ingestion.timeout_seconds` (300 — the per-file extraction wall-clock that a large PDF previously forced a source edit of), `ingestion.max_image_pixels` (100M, decision 17's decompression-bomb cap), `ingestion.max_file_size_mb` (**unset = no limit**; opt-in reject cap, the only new *behavior*), `llm.timeout_seconds` (300, httpx read timeout — local models are slow to first token), `retrieval.context_k` (8) and `retrieval.rerank` (true, decision's `--no-rerank` now also a persisted default). **Interchange-affecting knobs stay non-configurable** — `CHUNK_MAX_TOKENS`, `EMBEDDING_DIM`, the bge-m3/reranker pins: changing them is a re-index migration + manifest bump (architecture invariant), never a user tweak. The settings table is named `[ingestion]`, **not** `[extraction]`, to avoid colliding with the `extraction` provider call-class in `config set` dotted keys (the call-classes are a fixed enumeration — `chat/generation/extraction/router`, joined by `judge` at decision 30; `ingestion/llm/retrieval` never collide). Config **parsing** moves to `groundly/core/config.py` (a foundation both `llm/` and `ingestion/` import — this is parsing, not client construction, so the provider boundary holds); `groundly/llm/config.py` becomes a re-export shim. `groundly config` / `config set` are now implemented (were stubs); the writer regenerates the whole documented template from the effective config (`tomllib` is read-only), so no new dependency and the file stays self-documenting after every `set`. **No interchange change** — manifest and `format_version` unchanged.
19. **bge-m3 inference in fp16 + streamed per-document embedding** (Paul, 2026-07-20): `BGEM3FlagModel(use_fp16=True)` and the index pipeline stream vectors chunk-by-chunk into the per-file transaction instead of embedding a whole document at once. Motivated by a memray profile (`docs/superpowers/reviews/2026-07-20-ingestion-memory-perf.md`): resident-model RSS is a fixed ~2.3 GB fp32 floor, and FlagEmbedding pre-tokenizes + accumulates dense/sparse for whatever list it is handed, so a large single document drove peak RSS past 16 GB. **fp16 halves the floor to ~1.15 GB**; the M1 Pro executes fp16 natively (not emulated), so no CPU-latency cost. `BgeM3Embedder.encode_stream(texts, batch_size=64)` yields `(dense_numpy_row, sparse)` per chunk in bounded batches — kept as numpy fp32 (no `list[float]` boxing, ~8× waste) — and `store.add_indexed(..., chunks, vectors)` consumes that iterable lazily inside its single transaction, so **peak RAM no longer scales with document size**. Query and re-embed paths keep `encode()` (bounded already); both share `BgeM3Embedder`, so query and index compute in the same precision. Consequences: **interchange-contract change** — `manifest.embedding.dtype` `float32`→`float16` (records the *compute* precision; vectors are still stored as float32 BLOBs via `sqlite_vec.serialize_float32`). fp16 and fp32 vectors are numerically distinct, so `pin_matches` (pydantic equality over the `Embedding` block, decision 7) treats a float32 bundle as incompatible with a float16 subject — import re-embeds via the existing `re_embed` path. **No migration needed: no users / no existing corpora yet**; had there been, this is a full re-index. Storage schema, `format_version`, dim, chunking, and the hf_revision pin are all unchanged. A material file copied just before a transient embed failure can be left as an orphan in `materials/` (no store row); it is reused on the next-run retry, and — so an un-indexed original can never leak into a shared bundle — `export_subject` now ships only files that have a `materials` row (`bundle.py`, filters the `materials/` walk by indexed filename), rather than trusting whatever sits in the directory.
20. **litellm adopted as the LLM client inside `llm/`** (Paul, 2026-07-24): `groundly/llm/chat.py`'s `complete()` swaps its raw httpx POST for `litellm.completion()` — supersedes chat.py's old "raw httpx, no SDK" rationale, but does **not** reopen decision 8's three-framework rule: litellm is a provider *client* library used inside `llm/` (same boundary as before, .claude/rules/architecture.md), not a fourth orchestration framework, and it is already `graphrag==3.1.0`'s own transitive dependency (`litellm==1.86.2`, verified installed). Rationale: zero new installs; litellm's bundled price map (~2,700 models) gives automatic cost tracing for mapped cloud models with no per-token config; the manual `input_price_per_mtok`/`output_price_per_mtok` fields are demoted from "the only way to get cost tracing" to an override for local/unmapped models (`graphrag_adapter.estimate_cost` — moved to `llm/graph_cost.py` 2026-07-28 — falls back to `litellm.model_cost` the same way). Consequences: `LITELLM_LOCAL_MODEL_COST_MAP=True` is load-bearing for the privacy rule (grounding-and-privacy.md) — litellm's `__init__` otherwise fetches its price map from GitHub at import time, which would leave the machine; import stays lazy inside `complete()` (cold import ~2.5s — must never happen at MCP spawn); the split timeout is kept — litellm accepts `httpx.Timeout` directly, so 10s connect (dead host fails fast) + `llm.timeout_seconds` read (local models are slow to first token) pass through unchanged; `litellm` pinned exactly (`==1.86.2`) per the project's exact-pin convention for load-bearing deps.

21. **Graph prompt budgets derived from one configured context window** (Paul, 2026-07-25): `config.toml` grows a `[graph]` table with a single knob, `graph.context_window` (default **4096**, LM Studio's own common default), from which `llm/graphrag_adapter.prompt_budgets()` derives every graphrag prompt budget. Motivated by a real failure: on the `apd` corpus (1194 chunks) **every** extraction call returned `400 — Context size has been exceeded` from LM Studio, four runs produced `successful_response_count: 0`, and `~/.groundly/apd/graph/` was left with only `documents.parquet` and `text_units.parquet` — no entities, no graph, hours burned. Cause: `completion_model_config()` passed graphrag only provider/model/base_url/key, so every budget was graphrag's own, and those assume a large-context cloud model — entity extraction sends a ~1620-token few-shot preamble plus the chunk and then replays the whole conversation for a gleaning round, `summarize_descriptions` wants 4000 in + 500 out, and `community_reports` wants **8000 in + 2000 out**, i.e. ~16k of usable context to be safe. Each derived budget is `min(graphrag's default, a share of the window)`, so this only ever scales *down*: at 4096 peak demand is 3072 and gleanings are off (the replay roughly doubles peak context and buys little on a chunk capped at `CHUNK_MAX_TOKENS`), while at ≥16384 stock graphrag behavior is reproduced exactly. Two guards ship with it, because **graphrag swallows extraction failures per text unit** (`graph_extractor.py`'s `except Exception` → `on_error` → log) so they never reach `PipelineRunResult.error` and a graph missing most of the corpus would otherwise be stamped with a fresh `corpus_hash` and never rebuilt: (a) a **preflight probe** sends one real extraction prompt through `llm/chat.py` before the corpus run, turning a multi-hour silent failure into a named error in seconds; (b) a **failure gate** counts ERROR records on the `graphrag.index.operations.extract_graph` logger and refuses to stamp the manifest above 5% of chunks failed, reporting the count below it, with a missing or **zero-row** `entities.parquet` as a hard backstop (a zero-row parquet is ~1.9 KB of schema, so a file-size check would wave it through). Counting is filtered to the `.graph_extractor` child: one failed text unit emits *two* ERROR records under that tree (graph_extractor's `logger.exception` and extract_graph's `on_error`), which would otherwise halve the threshold and report more failures than there are chunks. A refused build deliberately **leaves its partial artifacts on disk** so graphrag's LLM cache survives the retry, so `retrieval/graph.py`'s `_require_graph` and the MCP `list_subjects` `graph_built` flag now gate on `manifest.graphrag.corpus_hash` rather than on the graph directory existing — otherwise the partial graph would still be served, which also closes the pre-existing case of a Ctrl-C'd build leaving a servable half-graph. **Completed 2026-07-27:** that conversion reached the two *query* gates and missed the two in `cli/subjects.py`, so a failed build's leftover `graph/` read as a stale graph — `graph_is_stale` answered "no graph has been recorded for this subject", and every later plain `groundly index` offered to *rebuild* something that had never existed, bypassing the `--graph` opt-in this decision's own artifact-retention created. `remove` carried the same predicate and promised a rebuild no index run would trigger. Both now read `manifest.graphrag.corpus_hash`, and `--graph` in that state correctly offers a *first* build rather than a rebuild. The lesson is the retention trade's second edge: once "the directory exists" stops meaning "there is a graph", **every** reader of that directory is wrong until converted, and the ones that only produce a message fail quietly. `build_graph` now returns `GraphBuildResult(chunks, failed)` so the CLI can report drops. **No interchange change** — manifest and `format_version` unchanged; the graph *content* differs with the window (smaller community reports at low settings), which is a quality/hardware trade, not a compatibility one. Two cost-estimate corrections ship alongside, both surfaced by pricing a cloud extraction provider for the first time: `estimate_cost` now adds graphrag's per-chunk few-shot preamble to the token count (it counted chunk text only, understating the real `apd` build **11.4×** — 186k tokens against 2.12M, because that corpus averages 156 tokens per chunk so the ~1620-token preamble is 91% of every call), and the litellm price lookup falls back to a *unique* suffix match. litellm keys OpenAI models bare (`gpt-4o-mini`, 517 of them) but everything else provider-prefixed (`groq/llama-3.3-70b-versatile`, 2199), and Groundly only ever knows the bare name because the provider is expressed as a `base_url` — so decision 20's "automatic cost tracing" silently applied to OpenAI alone. The match must be unique or it returns None, so two providers shipping the same bare name can never bill against the wrong price; this stays provider-agnostic, no hardcoding. **Superseded in part by decision 23 (2026-07-27):** both corrections stand, but the estimate they corrected was still input-only and still printed as a bare figure, which understated one measured build **76×**. A third fix came out of the first real cloud run (Groq, `llama-3.3-70b-versatile`, 2026-07-26): `allow_nonstandard_service_tier()` widens `graphrag_llm.LLMCompletionResponse.service_tier` from OpenAI's literal set to any string. graphrag_llm builds its response as `LLMCompletionResponse(**response.model_dump())` and types that field `Literal['auto','default','flex','scale','priority']`; Groq returns `'on_demand'`, so pydantic rejected **every** response — 258 requests, 258 failures, `No entities detected during extraction`, after the HTTP calls had succeeded and spent real tokens. Not a Groq special case: the field is provider-reported metadata graphrag never reads, and the construction site is a closure inside a factory function, so neither subclassing nor `register_completion` offers a seam — widening the field is the available fix, applied at both graphrag entry points (`ingestion/graph.py`, `retrieval/graph.py`, since global search makes its own synthesis calls through the same client). **The preflight probe structurally cannot catch this class**: it validates through `llm/chat.py`, which reads litellm's own permissive response model, so a provider whose *responses* graphrag can't parse still passes the probe. Finally, `completion_model_config()` now sets graphrag's `retry` and `rate_limit`, which it previously left unset: retry is always on (exponential backoff, 5 attempts, `base_delay=2.0` — graphrag rejects ≤1.0 — **with jitter**, since concurrent workers retrying in lockstep rebuild the burst that caused the 429), while throttling is applied only when `requests_per_minute`/`tokens_per_minute` are declared on the provider section, because limits are a provider/tier property with no portable discovery and guessing would throttle a local runtime that has none. Prompted by 283 failures out of 304 against Groq's free tier. Throttling cannot help with a **per-day** cap (Groq free = 100k TPD against `apd`'s 2.1M), which is a sizing decision, not a pacing one. A second swallowed-failure stage was then found the same way (DeepSeek `deepseek-v4-flash`, 2026-07-26): `create_community_reports` requests JSON mode, DeepSeek rejects `response_format` outright, all 22 report calls failed, and graphrag died merging the resulting empty frame — `KeyError: 'community'` — after a fully successful extraction pass. Community reports are what global search and `overview` answer from, and graphrag swallows their failures under `summarize_communities.community_reports_extractor`, a logger the extraction gate never watched, so a *partial* failure would have stamped a graph whose global arm had nothing to answer from. The counter is now generalized (`_WorkflowErrorCounter`, one per stage, as a context manager) and covers both stages; zero reports against a non-zero community count is a named refusal, partial failures are counted into `GraphBuildResult.reports_failed` and reported by the CLI; and the workflow-error message now quotes the last swallowed LLM error, since the workflow failure is the symptom and the per-item failures are the cause. `llm/chat.py`'s `complete()` grew a `json_object` flag so the preflight probe exercises that capability too — the third provider-capability gap in a row (`service_tier`, agentic-model 413, `response_format`) that a reachability-only probe could not have caught. **Corrected 2026-07-27:** that flag described the wrong capability and the probe it fed was never able to catch this. graphrag does not request `{"type": "json_object"}` — `community_reports_extractor` passes the Pydantic class `CommunityReportResponse`, which litellm converts unconditionally to `{"type": "json_schema", …, "strict": true}` (`llms/base_llm/base_utils.py`), because `completion_model_config()` declares `model_provider="openai"` and litellm's per-provider compatibility shims — Groq's json_schema→tool-call fallback, Vertex's — are all gated on the provider name and never run. Expressing the provider as a `base_url` is what buys Groundly its provider-agnosticism; bypassing those shims is the price, and it is the same structural cause as the `service_tier` bug. Measured against live endpoints on 2026-07-26, the two shapes are *not* nested capabilities but disjoint dialects: every DeepSeek model (`v4-flash`, `v4-pro`, `chat`, `reasoner`) accepts `json_object` and refuses `json_schema`, while LM Studio (`qwen/qwen3.5-9b`) refuses `json_object` and requires `json_schema` (`'response_format.type' must be 'json_schema' or 'text'`). So the `json_object` probe was simultaneously **too lax** — a `test_graph` build on 2026-07-26 passed it, spent 679s and 2.96M tokens on a flawless extraction pass, then failed all 436 community reports and was refused by the gate — and **too strict**, since it would have blocked a local LM Studio model that builds graphs fine, on the zero-key path that is meant to be first-class. `complete()` now takes a `response_format` passthrough and the probe hands it graphrag's own `CommunityReportResponse`, so litellm derives the identical wire request for probe and build and the two cannot drift; it also sets `enable_json_schema_validation=False` per call, since `graphrag_llm` turns that global on at import and it would otherwise fail the probe on the model's *answer* rather than the provider's acceptance of the request. Two secondary lessons recorded: capability is a property of the **model**, not the provider (on Groq, `llama-3.3-70b-versatile` has no schema support while `openai/gpt-oss-120b` does), and litellm's bundled capability map is not authoritative — it marks `deepseek-chat` as `supports_response_schema=True` and the live API rejects it, so the probe, not a table, is the answer. One more staleness hole closed after review: graphrag writes into an existing `graph/` without clearing it, so a build producing nothing left the *previous* build's parquet in place, and the artifact gates — which check that `entities.parquet` exists and has rows — passed on those and stamped a fresh `corpus_hash` over a stale graph (verified: a second build writing nothing and logging no failures inherited build 1's entities and was recorded as current for the new corpus). `_reset_graph_artifacts()` now drops everything under `graph/` except `cache/` (graphrag's paid-for LLM responses, which a retry must keep) and `logs/` (how a failed run gets diagnosed), **and resets `manifest.graphrag` in the same step** — clearing the artifacts while leaving the old hash would send `_require_graph`, which treats a non-None `corpus_hash` as "there is a graph here", hunting for parquet that was just deleted. It runs *after* the probe, so a misconfigured provider fails without destroying a graph that still works. Consequence: a rebuild that fails leaves the subject with **no** graph rather than the old one — correct, since a rebuild only runs once the corpus has already changed, so that graph was no longer a graph of this corpus. Course-appropriate entity types (graphrag's defaults are `organization/person/geo/event`, built for news) and build throughput remain open — the per-call preamble dominance above means throughput is driven by *chunk count*, not corpus size, and packing chunks would break the `document_id == chunk_id` citation mapping, so it needs its own spec.

22. **Course-tuned entity extraction, bundled and fingerprinted** (Paul, 2026-07-26): Groundly ships its own `extract_graph` prompt (`groundly/prompts/extract_graph.txt`, package data) and its own entity types, replacing graphrag's. Two problems, one change. **Cost:** graphrag's extraction prompt is 1,620 tokens sent *once per chunk*, and Groundly's chunks average 156 tokens against a 512 ceiling — so on `apd` (1,194 chunks) that fixed preamble was 1.93M of the build's 2.12M input tokens, **91% of the bill re-sent 1,194 times**. Inside it, instructions are 379 tokens and the three worked examples 1,236 (77%): the examples are the entire opportunity, which is why `community_report` (2,214/community, ~7% of spend) and `summarize_descriptions` (183/description) are deliberately untouched. **Quality:** the prompt was aimed at the wrong target — entity types `organization/person/geo/event`, worked examples a stock-market report and a political summit. Measured on a real default-prompt build of `test_graph` (355 chunks of parallel-and-distributed-algorithms material): 115 entities, 208 relationships, 23 communities, typed **75 ORGANIZATION, 34 EVENT, 4 PERSON, 1 GEO, 1 NONE** — zero concepts, zero algorithms, 95% news artifacts on material about mutexes, consensus and complexity bounds. The replacement keeps graphrag's instruction block and its `-Real Data-` tail **identical modulo trailing whitespace** (a test asserts this against `GRAPH_EXTRACTION_PROMPT`, so a graphrag upgrade that changes them fails rather than silently diverging; *amended 2026-07-30 from byte-identical, which broke on `73023cd` — a rename sweep that stripped the block's five lone-space lines and added a final newline. Upstream carries trailing whitespace this repo strips from every tracked file; it cannot reach the delimited record format, so tolerating it loses no detection while stopping the guard firing on repo hygiene*) — the delimited-record format is what the downstream parser depends on — and swaps the three news examples for **one** compact worked example on mutual exclusion, written as original prose because the file ships inside the wheel. The result is **696 tokens**, verified through the real `estimate_cost` path: `apd` 2,120,775 → **1,017,519** (2.08×), `test_graph` 658,016 → **329,996** (1.99×). A test caps the bundled prompt at 700 est. tokens, because this preamble's size *is* the build's bill and growing the example silently re-inflates every build. Examples are deliberately **not** dropped entirely: 417 tokens (3.9×) was available, but few-shot examples are what hold a model to the record format and unparseable output fails *silently per chunk* — the exact class decision 21 spent a day hardening against; one example is the trade. **This does not unlock a free tier** — `apd` at 1.0M is still ten days of Groq's 100k/day cap; it halves cost on any paid provider, halves local wall-clock, and retargets the graph. Default entity types become `concept,algorithm,data_structure,theorem,technique,tool,metric,person`; `person` stays (courses cite Dijkstra and Lamport), `organization/geo/event` go. Two optional `[graph]` knobs — `extraction_prompt` (a path) and `entity_types` — default to the bundled values, so zero-config behaviour is now Groundly's rather than graphrag's; they exist for two real reasons, a non-CS course needing different framing and the thesis evaluation, where **swapping the prompt is the experiment**. `entity_types` is a comma-separated **string, not `list[str]`**: `render_config_toml`'s `_toml_value` emits scalars only, so a list would round-trip through `config set` as a Python repr and corrupt the file. A custom prompt is validated at read time with a named cause before any LLM call — missing file, unreadable, or missing `{entity_types}`/`{input_text}`. It is also **refused for containing `{tuple_delimiter}`/`{record_delimiter}`/`{completion_delimiter}`**, which is counterintuitive and load-bearing: graphrag 3.1.0 formats the prompt with *only* `input_text` and `entity_types` (`graph_extractor._process_document`) and parses with hardcoded `TUPLE_DELIMITER`/`RECORD_DELIMITER` constants, so a prompt carrying one raises `KeyError` inside the per-chunk `except Exception` — every chunk failing, silently. The preflight probe formatted with those three keys and so was *laxer than the build it exists to predict*; it now formats exactly as graphrag does. The load-bearing half is **provenance**: `manifest.graphrag` gains `extraction_fingerprint` (sha256 over the resolved prompt text plus the entity types joined as graphrag joins them — in order, not sorted, since a reorder genuinely changes the prompt sent). `graph_is_stale` compared **only `corpus_hash`**, so a student could swap the prompt or the types and keep querying a graph built under different framing with nothing signalling it; it now compares both, and **returns a reason string rather than a bool** — telling someone "the corpus changed" when what they changed was `entity_types` is the same class of confident-but-wrong message decision 21's gates exist to prevent. `build_graph` records the fingerprint in the same write as `corpus_hash`, so a refused build records neither. The prompt is resolved through `importlib.resources.as_file()` in a context manager spanning the whole pipeline, because `ExtractGraphConfig.prompt` is a *path* graphrag re-reads at extraction time — correct for a zipped install as well as an unzipped one; a `@slow` test builds a real wheel and asserts the file is in it, since a missing prompt would work perfectly from a source checkout and fail only for an installed user. **No import change was needed**: import already preserves a bundle's whole `graphrag` block, so a differing imported fingerprint makes the graph stale at the next `index` with no new code — deliberately unlike the `corpus_hash` mismatch at `cli/sharing.py`, which *drops* the graph because that means the bundle's graph doesn't match its own `store.db`. **No interchange change** — additive-with-default, `format_version` stays 1 (precedent: decision 15's `ocr` block, decision 18's settings tables), and no migration is needed because no subject had a recorded graph: every `manifest.graphrag.corpus_hash` was still `null`. Out of scope and unchanged: `CHUNK_MAX_TOKENS`/`EMBEDDING_DIM`/the bge-m3 pin (interchange contract); chunk packing, which would cut calls further but breaks the `document_id == chunk_id` identity citation resolution depends on; and the 5% extraction-failure threshold, which a real run has already exceeded at 5.82% and should be set from evidence — changing it in the same commit would make a rising failure rate unattributable to the prompt. Honest limitation: the defaults lean CS-ward, which the override knob and the thesis text should both say plainly.
23. **The graph-build cost estimate becomes a range, and the trace becomes metered** (Paul, 2026-07-27): `estimate_cost` returns a `BuildEstimate` (low/high USD, both token counts, the price source, and any moving alias) instead of a single figure, the CLI prints every assumption behind it, and `build_graph` records what the build *actually* spent rather than what it guessed. Three compounding defects, one measured build to show what they cost together. On the `test_graph` run of 2026-07-26 23:40 (355 chunks, DeepSeek `deepseek-v4-flash`), graphrag's own metrics report **584,564 prompt / 2,371,523 completion tokens** — **$1.511** at the model's real rates — against a printed estimate of **$0.0198**. **76× under.** Decomposed: (a) *output tokens were not priced at all* — 94.2% of that bill was completion, so ignoring output alone is 17× on that run; (b) *the estimate covers the extraction pass only*, and metered prompt tokens were 1.77× the estimated ones once `summarize_descriptions` and `create_community_reports` were counted; (c) *the price map is bundled and stale* — litellm 1.86.2 has no `mistral-small-latest` key at all, only `mistral/mistral-small-latest` at $0.06/$0.18 per Mtok, while that alias resolves today to Mistral Small 4 (`mistral-small-2603`, 2026-03-16) at **$0.150/$0.600**, 2.5× and 3.3× low. 2.5 × 17 × 1.77 ≈ 75. Each defect was individually defensible and the product of the three was not, which is the whole lesson: conventions.md asks for a cost estimate before spending the student's tokens, and a number 76× under is worse than no number, because it is *believed*. **The upper bound is derived, not fitted.** Output volume is a property of the *model*, not the corpus — measured completion:prompt on the same corpus was 0.87:1 across four runs and **4.06:1** on the fifth (a reasoning model) — so any coefficient calibrated on one provider would be ~4.7× wrong on the next. The ceiling is instead `graph.context_window − preamble − CHUNK_MAX_TOKENS` per call, the room a call physically has left to answer in: 2,888 tokens at the 4096 default and the 696-token bundled prompt, and it moves with the window the way the real limit does. Re-derived through the real path: `apd` (1,194 chunks) is 1,017,519 in / up to 3,448,272 out, **$0.153–$2.222** at Mistral Small 4's rates against the **$0.061** the old line printed. **Honest limitation, disclosed on screen rather than papered over:** both ends price the extraction pass only. `summarize_descriptions` and `create_community_reports` are sized by the *extracted graph*, and the same 355-chunk corpus produced 23 communities on one build and 436 on another — a 19× spread that no pre-build heuristic can resolve. On the measured run the new upper bound is $0.664 against $1.511 actual, i.e. still 2.3× under, and the CLI says so in as many words ("extraction pass only — community reports and description summaries are billed on top, and cannot be sized before the graph exists") instead of inventing a number for it. Three disclosure rules ship with it: the price *source* is always named (`config.toml`, or `litellm <version>'s bundled price map ('<key>') — may be out of date`), because a price the student cannot attribute is a price they cannot sanity-check; an unpinned `*-latest` model gets an explicit **moving-alias warning**, since drift there is certain rather than possible; and the figure is printed to cents (tenths of a cent below $1, where cents alone round to zero), never the old `:.4f`, which claimed a precision a `chars // 4` heuristic does not have. It **warns, never blocks** — `typer.confirm` was already the gate and still is. A litellm entry carrying only an input price is now refused outright (`None`), because half-pricing would produce a range whose upper bound silently claims output is free; the same rule applies to the manual override, which now requires both `input_price_per_mtok` and `output_price_per_mtok`, matching `llm/chat.py` and `agents/decks.py`. Decision 21's unique-suffix matching is unchanged. **Metered actuals close the loop.** `build_graph` previously wrote the pre-build heuristic into `progress.db` behind a comment asserting exact usage was "unknowable here". It was not — `graphrag_llm` aggregates real per-model usage all along — but **the obvious way to get at it does not work, and fails silently**: graphrag only ever *writes* those aggregates from `MemoryMetricsStore._on_exit_`, registered with `atexit`, so both the log line and `MetricsConfig(writer="file")` land after the interpreter is done. A first implementation configured the file writer, read the JSONL after `build_index`, and passed its tests — which fabricated the file — while being unreachable in every real run; spec-guardian caught it before commit. `get_metrics()` has the same numbers *live*; all that was missing was a handle on the store holding them. Groundly therefore registers its own store type (`_ReadableMetricsStore` — renamed `ReadableMetricsStore` 2026-07-28, when `metered_usage`/`reset_metered_usage` moved to `llm/graph_cost.py` and the name began crossing a file boundary — a `MemoryMetricsStore` subclass that keeps a reference to itself) through `register_metrics_store`, exactly mirroring `register_bge_m3_embedding` — `completion_model_config(track_usage=True)` selects it for the build, the query path keeps the stock store, and the log writer stays on so the indexing log's end-of-run summary is unchanged. The trace now records metered tokens and cost, the CLI prints them after the build against the range it printed before, and the estimate remains the fallback whenever nothing was metered — telemetry must never be the reason an otherwise-successful build fails, and a store reporting zero tokens returns None rather than printing "$0.00", which would read as a fact instead of an absence. **Cache hits are subtracted from cost but not from tokens**: graphrag's totals count cached responses (one rebuild reported 420,965 prompt tokens at `cache_hit_rate: 1.0`, none of them paid for), and decision 21 deliberately preserves `cache/` across a failed rebuild, so retry-against-a-warm-cache is the normal path here, not an edge case. graphrag registers metrics stores as **singletons keyed on hashed init args**, so `reset_metered_usage()` zeroes the store at the start of every build rather than dropping the handle — a repeat build reuses that same store. That only holds while the `ModelConfig` is unchanged, so **one build per process** remains the real constraint (which is what `groundly index` does): change `extraction.model` between two in-process builds and graphrag constructs a second store while the handle still points at the first, reporting None rather than that build's totals. Documented at `reset_metered_usage`, because it is the same failure shape as the atexit trap — a silent wrong number with the tests green. **Superseded in part by decision 24 (2026-07-31):** the metering rework there tracks two completion models as separate stores, summed and priced per model, which repairs exactly this limitation — a changed model between two in-process builds now yields a new store while the cleared old one contributes zero, rather than reporting None. **Nothing is written to disk**, which keeps `graph/` exactly the parquet-artifact tree `docs/architecture/data-model.md` describes: the earlier file-based version would have quietly added the exporting student's build cost, failure rates and a local-timezone timestamp to every shared bundle, since `bundle.py` excludes only `cache/` and `logs/`. **No interchange change** — nothing here touches the manifest, `store.db`, `graph/`'s contents, or `format_version`; `progress.db` traces are inside the privacy boundary and never exported. The test for this drives graphrag's real completion factory and feeds the real store, deliberately not a stubbed output file: stubbing the output is what let the unreachable version pass in the first place. Out of scope: predicting community volume (see above), and vendoring or refreshing a price map — litellm's is the one we have, and naming its version is the honest handling of that.
24. **Reasoning is a configurable cost, and community reports can leave the extraction provider** (Paul, 2026-07-31): two `config.toml` knobs plus the metering fix they force. **(a) `providers.*.reasoning_effort`** — an optional passthrough string, forwarded as `extra_body: {"reasoning_effort": ...}` from `llm/graphrag_adapter.completion_model_config` (into graphrag's `ModelConfig.call_args`) and from `llm/chat.complete`. It must be nested: measured through litellm against Ollama, a flat `call_args={"reasoning_effort": ...}` raises `UnsupportedParamsError` for provider `openai`, and `drop_params` is False, so the flat form fails *every* call rather than degrading. The value is deliberately unvalidated — `"none"` is what Ollama honours, OpenAI's o-series takes `low`/`medium`/`high`, and an enum would reject valid provider-specific values, the same provider-agnosticism that makes `model_provider="openai"` right in the adapter. Motivated by measurement (2026-07-30, M1 Pro/16GB, Ollama, n=3, [review](superpowers/reviews/2026-07-30-local-extraction-feasibility.md)): disabling reasoning cut one extraction call from **386.5 s to 42.2 s (9.2x)** on `gemma4:12b` with output no worse — median 8 entities against 7, zero malformed records in all six calls — and community reports still 3/3 conforming, 4.4x faster, covering 7/7 input entities against 6/7 with reasoning on. The wall-clock ratio equals the completion-token ratio exactly (4,939 -> 536), i.e. the model was not reasoning its way to a better graph, it was spending nine tokens of deliberation per token of answer graphrag keeps; the extraction prompt asks for a delimited tuple list and has nothing to reason about. **This is not a local-only saving**: decision 23 already recorded completion:prompt at 4.06:1 on a reasoning model against 0.87:1 on four others, and output is ~94% of the graph bill, so the same tax bills as dollars on cloud. **(b) `graph.report_call_class`** (default `"extraction"`, validated against `CALL_CLASSES`) — names which call class serves graphrag's community-report stage; when it differs, `_build_config` registers a second entry in `completion_models` and points `CommunityReportsConfig.completion_model_id` at it, otherwise exactly one model is registered as before. The stages have **disjoint** requirements that one model had been forced to satisfy jointly: `extract_graph` is ~1,194 calls of plain delimited text that send no `response_format` at all (verified: the string appears nowhere in graphrag's `graph_extractor.py`), while `create_community_reports` is 23-436 calls of `json_schema`-strict output — the only stage needing schema support, and the stage where every recorded local failure happened. Chosen as a call-class *name* rather than a fifth `[providers.reports]` section because `CALL_CLASSES` is a fixed 4-tuple wired into the config template and `groundly config` display, and `chat` is already configured for `ask`, so `= "chat"` works with no extra setup. **(c) Metering had to change with it**, or the spend gate would lie: graphrag caches metrics stores as singletons keyed on hashed init args *including* the model id (`graphrag_common/factory/factory.py`'s `cache_key`, `graphrag_llm/metrics/metrics_store_factory.py` passing `"id": id`), so two models produce **two** stores. `ReadableMetricsStore.latest` became `instances`, `metered_usage()` sums across stores and prices **each by its own model**, and `reset_metered_usage()` clears them all — which also **repairs** decision 23's documented "one build per process" limitation, since a changed model now yields a new store while the cleared old one contributes zero. A store that ran but metered nothing (provider omitted `usage`) suppresses the cost rather than letting one model's bill print as the whole, keeping 23's rule that an absence must never read as a fact. **(d) The structured-output preflight probe now targets `report_call_class`**, not a hardcoded `"extraction"`. Probing the wrong provider reintroduces exactly the drift 23 closed, in both directions: too lax when extraction accepts `json_schema` and the report provider refuses (the whole extraction pass is spent before the first report fails), too strict when extraction refuses it and the report provider accepts — which would refuse the local-extraction/cloud-reports split this decision exists to enable. **(e) `manifest.graphrag.report_model`** records the second model when there is one, for the same reason `extraction_model` is recorded (data-model.md: a graph built by a different model is a different experimental condition) — community reports are what global search and `overview` answer from. Optional and additive, so old manifests parse unchanged: **no `format_version` event**. **The measured local floor, for the guides:** ~12B with reasoning *verified* off, at `graph.context_window` **12288** — the only value that both fits a community report (the stock template alone is 2,214 tokens, so a real 4096 window is over budget before any output) and keeps `max_gleanings` at 0, since it flips to 1 at exactly 16384 and makes extraction **two** LLM calls per chunk. Verification is per model, not per runtime: `"none"` suppresses deliberation on gemma and merely *relocates* it into the content channel on `qwen3.5:4b`. Going smaller is not the lever it looks like — `qwen3.5:4b` measured **4.8x slower** than the 12B (it emits 3-24x more tokens) with **1-44 malformed records per call** against the 12B's zero, and nothing catches that: graphrag drops malformed records silently and the 5% gate counts call failures, not dropped records. So the guide's old rule was right about *small* and wrong about *local*; cloud remains the default recommendation.

25. **A local graph build serializes: the prompt budget is per request, the runtime's limit is per cache** (Paul, 2026-08-01): `_build_config` now sets graphrag's `concurrent_requests` to **1 whenever any provider the build will call has a loopback `base_url`**, and to graphrag's own default (25) otherwise. Decision 24 raised the local floor to `graph.context_window` 12288 and showed the arithmetic by which a community report fits it; that arithmetic was correct and still produced a failed build, because it sizes **one** call and a llama.cpp-family server does not serve one call. Measured on `gemma-4-12b-qat` (2026-08-01, LM Studio, `test_graph`): the server loaded with `n_slots = 4, n_ctx_slot = 8192, kv_unified = 'true'` — four slots drawing from **one** 8,192-token cache, not 8,192 each — and graphrag dispatched all 11 level-1 communities at once. Report prompts measured 2,204/2,254/2,268/2,348 tokens, so four in flight demanded **~9,200 of an 8,192 cache**; llama.cpp walked its batch size 1024 → 512 → … → 1 and answered `decode: Context size has been exceeded. off = 108, n_batch = 1` — `n_batch=1` meaning it died mid-*decode*, not on prompt ingest. **8 of 11 reports were lost, in waves of exactly `n_slots`.** The controlled comparison is inside the same run and is what makes this a concurrency finding rather than a sizing one: the final wave had only **3** left, 3 × 2,300 = 6,900 < 8,192, and all three succeeded — identical prompts, identical model, the sole variable being how many were resident. Extraction survived the same build untouched because its prompts are 450–750 tokens (4 × 750 = 3,000), which is why the failure presents as a report-stage problem and sends the reader to `report_call_class` and JSON mode, neither of which is implicated. **Loopback is the signal, and it is a heuristic with a named gap**: a shared KV cache is what "the model runs on this machine" means, but `n_slots` is a load-time setting **no OpenAI-compatible endpoint reports**, so Groundly cannot compute the divisor and cannot see a local runtime reached over the LAN — that case keeps 25 in flight and needs the server's slots reduced by hand, which the guide says in as many words. It errs the other way too — a cloud provider behind a local proxy serializes when it need not — and that asymmetry is deliberate: the false negative loses a build, the false positive loses only throughput on a path that has none to lose. The setting is variadic and pessimistic (**any local provider wins**) because graphrag has exactly one global `concurrent_requests` covering every stage, so a local extraction model binds the whole build even when 24's split points reports at a cloud one. **Serializing is close to free on the hardware it applies to**: prompt-eval measured ~150 tok/s with one slot busy against 30–60 tok/s with four contending — they share the same GPU either way — so the cost is bookkeeping, not throughput, and the cloud path is untouched at 25. **Three supporting changes, each independently justified by the same run.** (a) `_retry_config` drops `BadRequestError` from graphrag_llm's never-retry defaults: a local runtime reports *capacity* exhaustion as a 400, litellm maps it to the same class as a malformed request, and the metrics block records `"retries": 0` — a transient error classified as permanent. The evidence that retrying is right is the 3-in-flight wave succeeding unaided; a backed-off retry recreates exactly those conditions. The cost when the 400 *is* structural is 2/4/8/16/32 s before it surfaces, bounded and screened up front by the probe, which calls `llm/chat.complete` (litellm directly, **not** graphrag's retrier) and is therefore unaffected. (b) `llm/chat.loaded_context_length` reads LM Studio's own `GET /api/v0/models` after the first probe call — **after**, because a local runtime JIT-loads on first request and reports "not loaded" before it — and warns when the served window is smaller than `graph.context_window`. Observed on this run: config said 12288, the server was serving 8192 after a reload. This is an unusually literal reading of "never hardcode a provider": the rule protects the *call* path, where a hardcoded provider makes endpoints unusable, and nothing here reaches an LLM or gates a build — any endpoint that 404s, times out, or answers an unrecognised shape returns `None` and the build proceeds. It warns rather than refuses for the same reason, and it only became a *meaningful* number once concurrency was fixed, since before that it understated real demand ~4×. (c) `_report_failure_hint` names concurrency in both the zero-reports refusal and the partial-failure warning when the last error mentions a context limit; the previous message blamed JSON mode, which is the right guess for a provider that refuses the request outright and the wrong one here — it is what sent this investigation to tune `graph.context_window` first. **No interchange change**: nothing touches the manifest, `store.db`, `graph/`'s contents, or `format_version`, and no new `config.toml` key is introduced — a derived default was chosen over a tunable precisely because the number users would have to supply (`n_slots`) is one they cannot read off the endpoint either.
26. **The knowledge graph gets a picture, and it ships its own renderer** (Paul, 2026-08-02): `groundly export-graph SUBJECT` writes ONE self-contained HTML file — entity nodes coloured by Leiden community, force-directed, sidebar carrying each community's report and each entity's citations back to document + page/heading. Generator in `core/graph_html.py` beside `core/anki.py` and `core/bundle.py`, the other two "render an artifact to a file" modules; CLI holds the verb only; citations reuse `SubjectStore.chunk_details()` rather than new SQL. Motivated by an operational gap, not aesthetics: the parquet artifacts were readable only by the query path, so **a build that quietly extracted nonsense looked identical to a good one** — the 2026-08-01 build (decision 25) lost 8 of 11 community reports and still reported success. **This is not the P7 dashboard**, which stays a `serve`-hosted page; a one-shot CLI export needs no FastAPI wiring. **The vendoring is the architectural commitment.** graphify's equivalent page loads vis-network from unpkg, which would make every *view* a third-party request disclosing that the student is looking at a knowledge graph, plus their IP and the time — not one of the three egress paths `.claude/rules/grounding-and-privacy.md` permits, and fatal to a page meant to open offline months later. So vis-network 9.1.6 (Apache-2.0 OR MIT, 702,611 bytes) is checked into `groundly/assets/`, SHA-384-verified against the SRI hash graphify itself pins, inlined at generation time, with provenance in `assets/VENDORED.md` — the repo's first vendored third-party blob, and the precedent for any later one: pinned, hash-recorded, and guarded by a test (`test_page_references_no_external_url`) that fails if a CDN reference is ever reintroduced. **Two measured decisions inside it.** (a) *Escaping `<` is sufficient and `>` must stay*: entity text is layer 4 and `groundly import` is a trust boundary, so a hostile bundle can carry an entity named `</script><img onerror=…>`; all data is embedded as one `json.dumps` blob with `<` -> `\u003c` and the JS touches the DOM only via `textContent`, never `innerHTML`. Per the HTML spec the script-data end-tag-open state requires `</`, so removing every literal `<` makes early termination impossible — verified on a real export, 3 `</script` occurrences, all genuine closing tags, none inside a script body. `>` is left alone because a bare `>` cannot start a tag; escaping it would have been safe but pointless, and the test asserts the *structural* property (no `</script` in any script body) rather than one spelling of the escape. (b) *`level=None` resolves to the coarsest Leiden level, not the finest* — the intuitive choice is the wrong one, because Leiden only subdivides communities large enough to split, so every deeper level covers strictly fewer entities and the rest render grey. Measured: `test_graph` colours 81/114 (71%) at level 0 against 41/114 (36%) at level 1; `gm-validate` 188/385 (49%) at level 0 against 12/385 (**3%**) at level 2 — defaulting to the finest would open that subject as an almost entirely grey graph. Above `_MAX_NODES = 5000` entities the community meta-graph is rendered instead and the CLI says so, never silently. **Reviewed adversarially before commit**, and the reviews are the interesting half. The XSS defence and the privacy boundary both held under a purpose-built hostile subject and instrumented `open`/`sqlite3.connect` tracing. What broke was everything around them: citations were **silently dropped** wherever `text_units.id` collided (it is a content hash, so byte-identical chunks share one — 10 entities on gm-validate lost *every* citation while the page still claimed to resolve them); a partial build tracebacked instead of naming its cause; and resource bounds were missing entirely, since `_MAX_NODES` caps how many things are drawn and not how big each is (100 entities, 50x under the cap, with 1 MiB descriptions produced a 300 MiB page). All fixed — `_MAX_FIELD_CHARS` bounds the output, `_read_bounded` streams row-group batches against a 512 MB ceiling, and a 5 GiB expansion is now refused in 0.11s at 847 MiB peak. One wrong turn is recorded deliberately: the first bound used parquet's footer `total_byte_size`, which reports the *encoded* size — 600 identical 1 MiB strings dictionary-encode to 1.02 MiB against 600 MiB actual — so it passed the very attack it existed to catch, which is worse than no check at all. **The vendored blob lives in `groundly/assets/`, not `web/static/`**: `web/` is a named client layer, and a foundation module reading its data is a coupling no import graph would ever surface; `prompts/` is the precedent that actually applies. **The hash test earned itself within the hour** — an IDE format-on-save expanded the pinned file from 702,611 to 1,160,728 bytes and the test caught it, which is precisely why a hash recorded only in prose is not a pin. **No interchange change**: nothing touches the manifest, `store.db`, `graph/`'s contents, or `format_version`, and the exported HTML is derived wholly from artifacts that already export — `progress.db` is never read, so a shared page cannot leak quiz history or query traces.

27. **The eval harness is a fourth client, and its first run invalidated the arm comparison it was built to make** (Paul, 2026-08-03): `groundly eval SUBJECT --gold PATH --arms ...` scores retrieval arms against a labelled gold set. Harness in **`groundly/eval/`** — a *client*-layer package alongside `cli/`, `mcp/`, `web/`: it imports `agents`/`retrieval`/`core` and nothing imports it, so the one-way dependency rule holds and `.claude/rules/architecture.md` gains a fourth name rather than a new layer. It is a research surface, not a product surface — no MCP tool, no runtime path. This closes P5's verify criterion, which had been open since the graph landed: the build worked, the arms ran, and **nothing had ever been measured**. **The one product-path change** is `retrieve_for_arm(subject, query, arm, ...)`, lifted out of `ask()` unchanged, plus `ask(arm=...)` which skips the router. The router speaks query classes and the retrieval layer speaks arms; keeping the vocabularies separate is what lets the eval force an arm without fabricating a router label, and the `traces` schema had already separated `router_label` from `arm` (P3) in anticipation. An unknown arm raises rather than falling through to vector — a typo in `--arms` silently scoring the baseline three times is the failure mode that would be hardest to notice in a results table. That guard was itself defeated once: adding per-question error tolerance put an `except Exception` around the call, which absorbed the very `ValueError` the guard raises and filed a typo'd arm as a provider outage, results file and all. `run()` now validates every arm before the first question, and re-raises the exception classes that mean *this code is broken* (`KeyError`, `TypeError`, `AttributeError`, …) instead of scoring a broken arm as a flaky one — `TypeError` being exactly how the text-unit collision below presented. **Gold set: 48 questions labelled by `(filename, page)`, never chunk id** — chunk ids are SQLite rowids that shift on re-index, filenames and pages survive one, and labels resolve against the live store at run time. Provenance: `Examen.md` 23, `Quiz 1 - ThreadsSynchro.pdf` 7, `Quiz 2 - OpenMP.pdf` 1, `REZUMAT.md` 1, plus 16 hand-written (8 RO cross-lingual, 8 EN filling the global and RAFT/sockets gaps the quizzes leave); stratified 17 factoid / 22 multi-hop / 9 global, 39 EN / 9 RO. **The contamination guard is load-bearing and non-obvious**: the exam files are *themselves indexed*, so a question lifted from `Examen.md` retrieves `Examen.md`, and that "hit" is the question, not the answer. `gold.py` rejects any row whose `expected` names **any** file the gold set draws questions from, and `metrics.leakage` separately counts how often an arm retrieves one anyway — **13.5% for the vector arm** (factoid 11.0 / multi-hop 17.1 / global 9.7), with 37 of 48 questions retrieving at least one exam chunk, reported rather than suppressed. Both the guard and the metric are corpus-wide because the first version scoped them per row and understated contamination by ~37% (10.0% reported against 13.5% real): `source_file` was one optional string, so a question appearing verbatim in two indexed files counted only one of them (apd-006 is in both `Examen.md` and `Quiz 2`, and the vector arm returned both at ranks 1 and 2), and the 16 of 48 rows that are hand-written declare no source at all — those reported exactly 0.0 by construction while still retrieving exam text. A declared source that resolves to no chunk now warns instead of silently measuring against an empty set. **First measured baseline (vector arm, zero-key, 48 questions):** hit rate 94% factoid / 59% multi-hop / 56% global, recall 0.76 / 0.39 / 0.22, MRR 0.49 / 0.30 / 0.17. That degradation curve is precisely the gap the graph arms exist to close, and it now has a number attached instead of a hypothesis. **The finding that changed the harness:** `graph-global` returns **1,138 of the subject's 1,193 chunks — 95% of the corpus — for every question**, against the vector arm's `context_k` of 8. Its recall of 1.00 and hit rate of 100% are artifacts of returning nearly everything, and `retrieved_n` is what exposes that. **The first draft of this decision credited MRR (0.02) with exposing it, and that was wrong** — an adversarial review reproduced the entire published graph-global row offline with zero LLM calls, because the arm ends its citation join with `sorted(chunk_ids)` and the resulting "rank" is ascending SQLite rowid. Its MRR measured how apd was indexed, and the per-class split (factoid 0.010 vs global 0.043) said only that global questions carry lower-numbered labels. Arms in `retrieval.arms.UNRANKED_ARMS` now report `mrr = None`; withholding a metric is the honest move when the arm has no ranking for it to read, and it stops being withheld the moment global search ranks its output. This is the P5 design spec's flagged open risk (`retrieval/graph.py`'s global citation join pools every text unit of every entity in every used community) measured for the first time and far worse than "broader than what informed the answer". Consequences: `retrieved_n` became a first-class metric, the CLI prints an explicit non-comparability warning when arms differ >4x in set size, and **a hit-rate-only table would have reported graph-global as a triumph** — the exact false result the harness exists to prevent. Narrowing the join is deferred, deliberately: it is a documented decision, not a patch. **A sibling-caller bug fell out of the first run**: `GraphGlobalRetriever` resolved text units with `set_index("id")["document_id"]`, which returns a *Series* for the content-hash collisions decision 26 already documented and fixed in `core/graph_html.py` — `int()` then raises `TypeError` and global search fails outright (apd: 18 of 1,193 ids collide; "REVIEW" heads two quiz decks). 26 found it in the export path and never carried the fix across; both joins now build `id -> list[document_id]`, and the regression test asserts *both* colliding chunks are cited rather than one silently winning. **Provider requirements are asymmetric, and the first draft of that claim was wrong in the way decision 23 exists to prevent**: `vector` is genuinely zero-key, and both graph arms reach the `extraction` provider *inside* graphrag's own search call — spend that never passes through `llm/` and lands in no trace row. The warning first said "once per question" for both. That holds for `local_search` and is wrong by ~33x for `global_search`, which is **map-reduce over the community summaries**, batched to `GlobalSearchConfig.max_context_tokens` (12,000, unoverridden): apd's 555 reports at `level <= 2` total ~389k tokens, giving ~33 map calls plus a reduce **per question**, i.e. ~1,600 untraced provider calls across a 48-question sweep rather than 48. Caught by `spec-guardian` before commit, which is the second time a confidently-stated cost figure has been the defect (23's 76x) and the reason the CLI now prints the two arms' costs separately instead of averaging them. Measured latency on the local floor (`gemma-4-12b-qat`, LM Studio): ~165 s per graph query against ~7 s for vector — a 48-question, two-graph-arm run is ~4.4 hours, which is the argument for the vector arm staying provider-free. **Three of the harness's own numbers were themselves unfair, and fixing them cost less than the arm it was measuring** (2026-08-08, following a performance review of the graph arms): (a) **`hybrid-local` was paying for an answer nothing read.** graphrag's `local_search` builds its whole context, fires `on_context`, and only then streams prose — which `retrieve_for_arm` discarded before `ask()` generated its own. `_AbortAfterContext` raises out of that callback: **chunk ids byte-identical on every question tested, 33–49x faster** (152–208 s → 3.6–6.2 s contended, 0.21–0.45 s for the graph half idle), and the arm is now **zero-key**, closing its untraced-call gap. There is no equivalent for `graph-global`: its `on_context` fires *after* the map phase, so the reports its citation join needs only exist once the expensive work is done. (b) **The published arm comparison was not set-size-matched.** It put vector's 8 chunks against hybrid-local's untruncated 33 (`ask()` never applied `context_k` — a live defect, and `graph-global`'s 1,138 chunks would have pushed ~183k tokens into a 16,384-token window) and against a claimed `vector@32` that **cannot exist**, because `RERANK_POOL` caps the pool at 20 before `context_k` is read. `retrieve_for_arm` now returns each arm's full candidate list, the consumer applies `context_k`, and `metrics.sweep` scores every cutoff from one run. (c) **Two metrics were confounded and one delta was noise.** Leakage is now read against the corpus base rate (apd: 45/1,193 = 3.77%), because an arm returning 95% of the corpus scores at the base rate by construction and *looks cleanest*; the vector arm's 13.5% is a 3.6x enrichment. And the review's headline "net -3" is **5 discordant pairs, exact McNemar p = 0.375** — at n = 48 this gold set cannot resolve a difference below ~9 questions, which is the honest claim and a stronger one. The negative result survives all three corrections and gets sharper: on the first fair run (48 questions, both arms zero-key) **`vector` beats `hybrid-local` at every matched cutoff on every metric** — k=8 71% vs 60% hit, 0.49 vs 0.38 recall, 0.34 vs 0.26 MRR; k=20 90% vs 81%. At natural set sizes the same run reads the *other* way (92% vs 90% hit) purely because hybrid returns 42 chunks to vector's 20, which is the set-size artifact stated as plainly as it can be. Still nothing clears p < 0.05 (best k=20, p = 0.125), so the claim is "the baseline leads consistently and n = 48 cannot certify it", not "graph loses by X". A separate finding fell out of the base-rate correction: **contamination concentrates at rank 1** — the vector arm's top chunk is exam material at **14.9x** base rate, decaying to 2.5x by k=20. And measuring the router for the first time found it **47.9% accurate against 45.8% for always answering "multi-hop"** — one question better than a constant — routing **30 of 48 questions to `global`** (a class holding 9): the arm that returns 1,138 chunks at ~33 untraced calls each. So the `assemble()` overflow was the majority product path, not an edge case, and the oracle's headroom over always-vector is 3 questions at k=8, inside what n = 48 can resolve. Vector-only is the honest default configuration on this corpus. **The at_k table and the significance test both exclude unranked arms** for the same reason MRR is withheld from them: truncating `sorted(chunk_ids)` yields the k lowest rowids in the corpus, a number that reads as precision@k and measures ingestion order — the first draft of this very fix computed it. Latency, correspondingly, is only reported within single-arm runs: a resident local model is a 5.4x tax on every other arm (reproduced during this work — a 262k-context 12B held loaded slowed the provider-free arms ~5x).

**The verb ships to students**: hatchling packages the whole tree, so `eval` appears in every `groundly --help`. "Research surface, not product surface" is an architectural intent about dependencies, not an enforced packaging property.

**Two failure modes the first real runs taught, both now tested**: (a) a single question must not destroy the run — the first full sweep died ~20 minutes in on one context overflow (LM Studio serving 8,192 against `graph.context_window` 12288, exactly decision 25(b)'s condition) and wrote nothing at all; errors are now recorded per question, **excluded from every quality metric** so an outage cannot read as an arm retrieving badly, and reported before the table. (b) `KeyboardInterrupt` keeps what ran and marks the results `partial`, because a half-run silently indistinguishable from a full one is the one outcome worse than losing it. **RAGAS, citation accuracy, cost/latency-from-traces and the grounding-fidelity experiment are slice 2**, and `retrieval/adaptive.py`'s arm-4 stub stays a stub until there is a harness to measure it against — which there now is. **No interchange change**: no manifest field, no `store.db` schema, no `format_version` event; `progress.db` is untouched by retrieval-only runs, and gold sets are versioned in `evals/<subject>/gold.jsonl` while the results they produce are gitignored.

Consequences for the arms: anchoring gets **worse** (`top_k_entities = 10` is now 0.16% of entities, 18.6% of which are traversal-dead), and `graph-global` gets **more expensive** (reports at level ≤ 2: 555 → 941, so ~33 map calls per query become ~56) while its 1,138-chunk constant is untouched. Isolating model from procedure needs one further build at `context_window` 12288; until then the re-measurement is of model+procedure. If it overturns the `hybrid-local` half, re-admitting the arm is one tuple entry. **Deliberately unchanged**: `retrieve_for_arm` keeps all three arms and `groundly eval --arms vector,hybrid-local,graph-global` keeps working (the negative result must stay reproducible from shipped code, and `eval/` is a client that may depend on services); `drill_down`/`overview` (UC-12) are untouched, reaching the retrievers directly via `agents/study_modes.py` — that structural use is the graph's remaining justification; `retrieval/graph.py`, `UNRANKED_ARMS`, and `llm/rerank.py`'s `use_fp16=False` all stay. **No interchange change**: no manifest field, no `store.db` schema, no `format_version` event.

29. **Every implemented arm is selectable; `vector` becomes the default rather than the only choice** (Paul, 2026-08-11): `ask(subject, query, arm=VECTOR, ...)` and `groundly ask --arm` are back; `Arm.product` and the derived `PRODUCT_ARMS` are deleted, and with them the product/research split decision 28 introduced. **The decisive reason is that the split blocked the thing it existed to serve.** Decision 27's slice 2 — citation accuracy, faithfulness, cost per answer — is measured from full `ask()` runs reading the traces table, and with `ask()` hard-wired to `vector` there was no way to produce those numbers for any other arm. The comparison *is* the contribution, so a structure that caps it at retrieval costs more than it protects. The alternative was duplicating the ask pipeline inside `eval/`, which would have made the measured pipeline a different pipeline from the shipped one — the exact property decision 27 built the harness to avoid.

**What decision 28's measurement still buys**: `vector` is the default because it led hit and recall at every cutoff the product uses, so the zero-key, zero-build arm is what a student gets without asking for anything else. Nothing about the published numbers changes.

**`graph-global` is scoreable but not askable, and the reason is mechanical, not editorial.** It emits `sorted(chunk_ids)` — ascending SQLite rowid, no relevance order (`UNRANKED_ARMS`, already why it is excluded from matched cutoffs and significance) — while `ask` truncates to `context_k`. Together those mean an `ask --arm graph-global` would ground every answer, for every question, in whichever 8 chunks sort first: a corpus constant dressed as retrieval, and a *cited* one, which is worse than an obvious failure. It would also add ~56 untraced graphrag calls per query to the product path, understating the trace's own cost column. `validate_arms(..., ranked_only=True)` is the gate and it reads `Arm.ranked`, so if global search ever ranks its output the arm becomes askable with no further change. The eval keeps scoring it on the order-insensitive metrics that stay honest.

**Degradation is deleted as a concept.** It existed only inside `retrieve_for_arm`, which caught `GraphNotBuiltError` for a `needs_graph` arm and returned the vector arm's nodes under the graph arm's name. Both callers wanted it gone — the eval already treated it as fatal (`ArmDegradedError`, now deleted), and someone who typed `--arm hybrid-local` does not want the baseline's numbers under that label. So `retrieve_for_arm` returns `(nodes, path)`, the arm that ran is always the arm that was asked for, and `GraphNotBuiltError` propagates. `ask()` and `eval.runner.run()` each **preflight** it — before the trace opens and before question 1 respectively — so a run that cannot work costs nothing, loads no model and leaves no record. `Subject.graph_is_built()` is the shared predicate (directory **and** recorded `corpus_hash`, since a refused build deliberately leaves partial parquet behind); `retrieval/graph.py`'s `_require_graph` and `mcp/server.py`'s `list_subjects` now read it too. The narrower manifest-only checks in `ingestion/graph.py` and `cli/subjects.py` deliberately do **not** — folding the directory term into them would make `graph_is_stale`'s "the graph directory is missing" branch unreachable. **A consequence worth recording: `ask` and the study modes now disagree about tracing a missing graph.** `ask` preflights, so it writes no row; `drill_down`/`overview` raise the same `GraphNotBuiltError` from *inside* `TracedAnswer` and write an error row. That is not an oversight — those two reach the retrievers directly (`agents/study_modes.py`) and have no arm to preflight on — but it means `agents/tracing.py`'s "every outcome is traced" now holds for them and not for `ask`.

**The router stays off the ask path** (28's other half), now on its own merits rather than by structural default: 47.9% against 45.8% for a constant classifier, and 30 of 48 questions routed to the most expensive arm. With `--arm` stating the arm outright, a classifier would spend a provider round-trip guessing at something the caller already said.

**Deliberately unchanged**: the MCP `ask` tool keeps its signature and stays on `vector` — a host model picking a graph arm on a whim spends the student's tokens without being asked, and graph access from MCP is `drill_down`/`overview` (UC-12), which exist for exactly that. No `groundly search --arm`: `groundly eval` is already the retrieval-only measurement tool, and `search` is the zero-key path. Arm 4 (`adaptive`) stays `build=None`. **No interchange change**: no manifest field, no `store.db` schema, no `format_version` event.

30. **The grounding-fidelity experiment measures enforced `ask` against a real MCP host, not against a scripted prompt** (Paul, 2026-08-13): `groundly eval-grounding SUBJECT` runs the same gold questions down both paths — (a) the enforced `ask` pipeline, (b) a cold `claude -p` session per question with the groundly MCP server attached and its tool allowlist pinned to `search` — and compares them on faithfulness, attribution and refusal rate. Harness in `groundly/eval/{attribution,judge,grounding}.py`; `docs/architecture/retrieval.md` carries the protocol. This is the only measurement in the thesis that tests Groundly's central design bet rather than comparing retrieval arms against each other, and **a negative result is the finding, not a failure** — if enforced grounding does not beat a competent host on the same corpus, the MCP `ask` tool's justification weakens and that is worth publishing.

**Path B is a real host, and the alternative was the easy way to a meaningless number.** A scripted "answer from these sources" prompt would have been cheap, fully reproducible and publishable verbatim — and would also have let the enforced path win by construction, because the result is only as credible as the thing it beat. The cost of choosing fidelity is stated rather than hidden: **the host's own system prompt is Anthropic's, is not publishable, and drifts between CLI versions**, so the run is re-runnable (same argv, pinned model) but not frozen. The results file records the `claude` CLI version, the model id and the full argv; the thesis states the limitation. **Host isolation took three attempts, each wrong answer disproved by running it, and the sequence is worth recording because every step sounded right.** (a) `--allowedTools mcp__groundly__search` alone does *not* block `Read` — measured, a host with only that flag read a canary file in its working directory. It is a permission allowlist over the MCP surface, not a restriction on what exists. (b) `--tools ""` blocks `Read` and **also disables the MCP tools**, so the host answers "no such tool is available to me" and the experiment measures nothing; the same prompt without it returns 8 chunks. A fix that silently removes the thing being measured is worse than the hole it closes. (c) What actually works, both verified: `--disallowedTools Read Write Edit NotebookEdit Bash Glob Grep WebFetch WebSearch Task` (blocks `Read` in the cwd, leaves MCP search returning 8) **and** an empty temp directory as cwd (Claude Code scopes file access to the working directory — an absolute path to the gold set is refused). Two independent guards, neither relied on alone. **The experimental stake exceeds the security one**: with `Read` live and the host inheriting the sweep's cwd, path B could open `evals/<subject>/gold.jsonl` — the answer key, naming the file and page of every expected answer — and would have scored brilliantly for reasons having nothing to do with composing from `search`, with nothing in the output showing it. The restriction is additionally *verified* rather than trusted: the harness reads the trace table for an `ask` row in the host's window and voids that question if one appears.

**`--bare` was dropped in favour of `--setting-sources "" --disable-slash-commands`.** Both strip the local configuration that must not reach the host under test — CLAUDE.md, hooks, plugins, output styles, skills — but `--bare` forces auth to `ANTHROPIC_API_KEY` alone, refusing the subscription login most students have, and isolation that costs the ability to run the experiment is not isolation. Measured on the development machine: **46,555 tokens of inherited context without these flags, 8,935 with them.** Flags: `--setting-sources ""` (no hooks, no CLAUDE.md discovery, no plugins or output styles — otherwise the host under test inherits the operator's local configuration, which is unpublishable and changes the answer), `--strict-mcp-config`, `--allowedTools mcp__groundly__search` (mechanically prevents path B calling the pipeline it is the control for), and one cold process per question (a single session would answer question 12 from chunks read at question 5, a contamination invisible in the output and impossible to subtract afterwards). The task prompt is ours and published verbatim; **it says nothing about citing**, because whether an unprompted host attributes at all is one of the things being counted. The host is not left uninformed — the `search` tool's own description tells it grounding is not enforced there — and being told that by the product at the moment of use is exactly the condition under study.

**The host searches as often as it likes**, and the matched comparison is a sub-analysis rather than an enforced protocol. Constraining it to one call would isolate composition from retrieval perfectly and would measure a host nobody ships. Every `search` is already traced (`retrieval/vector.py`, unchanged), so `n_searches` and the union of chunks it saw are read back out of the traces table — **path B needed no product change at all**. The paired McNemar test is then reported twice: on the matched subset (questions where the host saw everything `ask` saw) and on all questions, each with its n. Verified on apd: `search` at default `k` returns exactly the 8 chunks `ask` grounds in (6/6 questions checked), because `_build_vector` reranks a `RERANK_POOL`=20 pool and both paths take a prefix of the same reranked order.

**Citation accuracy is asymmetric by construction, so it is reported as three layers rather than one number.** `ask` is mandated to emit `[chunk N]` and `agents/citations.py` raises if none resolve; a host cites filenames, pages and `groundly://` uris in prose. A single "citation accuracy" metric scores path B near zero *by definition of the regex* and proves nothing. So: **present** (any attribution at all), **resolvable** (does it map to a chunk actually retrieved), **supported** (does that chunk support the claim). **Both paths go through one extractor** (`eval/attribution.py`), which scans for the corpus's known filenames as literals rather than guessing at filename shape — necessary because filenames here contain spaces, so `groundly://apd/Curs 3.pdf#page=4` is not a parseable uri and a `\S+` regex truncates it. The **resolvability gap is itself the finding** and is framed as one.

**Refusal rate is a headline column, never a footnote.** The enforced path refuses by design; a refusal makes zero claims and would score as perfect faithfulness if faithfulness were a bare mean. That is the single most likely way these numbers could lie in Groundly's favour, so `Verdict.faithfulness` returns `None` rather than 1.0 for a no-claim answer, and the CLI prints refusal immediately beside faithfulness.

**The judge is ours, pinned, blind and run twice — bought directly with decision 28's retraction.** A new `judge` call class (`CALL_CLASSES` 4 → 5, one added commented section in the rendered config template and one row in `groundly config`, nothing else) so the judge can be a *stronger* model than the one under test and so "which model judged this" is a configured fact the results file reads back rather than an inference. It is called through `llm.chat.complete()`, inside the provider boundary. Per answer it splits claims and returns a per-claim verdict plus the supporting chunk — one pass yielding both faithfulness and attribution layer three, since "was this claim's support a chunk the answer actually cited" is a comparison between the two. A `supporting_chunk` the judge invents is dropped and the claim goes unsupported: the judge hallucinating would credit an answer with support from a chunk nobody read, which is the failure under study arriving through the instrument. Answers are stripped of attributions before judging so the judge cannot classify by spotting `[chunk N]` — **blinding is partial and is documented as partial**, since it cannot hide two paths' house styles; the judge's self-agreement across two runs and a human spot-check of ~15 blinded, shuffled answers are what the numbers actually rest on. **ragas was rejected**: it is a declared optional extra and `retrieval.md` already named it, but it constructs its own LLM client (forbidden outside `groundly/llm/`, and its calls would bypass the traces table) and versions its prompts upstream, so a ragas upgrade would silently change a published number.

**`tests/test_layering.py` was scoped, deliberately.** It asserted that no file under `eval/` imports `groundly.agents`, which read as a layer rule but was not one — `.claude/rules/architecture.md` puts `eval/` in the client layer and `agents/` in the service layer, and clients may import services. What it protected was the retrieval sweep's *generation-free* property, still worth pinning since a graph-arm sweep runs for hours and must not load a chat client it never calls. The assertion now names `runner.py`/`metrics.py`/`gold.py`, with a second test failing if one of those is renamed so the exemption cannot pass vacuously. `eval/grounding.py` calls the real `ask()` rather than a copy — decision 29 anticipated exactly this ("generation-side metrics come from full `ask()` runs"), and duplicating the pipeline inside `eval/` would have made the measured pipeline a different pipeline from the shipped one.

**Verified additive** to the standard PRs #31/#32 set: re-running `groundly eval apd --arms vector` after the change reproduces the 2026-08-09 baseline's per-question chunk id lists **48/48 identical**; the config template gains exactly one commented `[providers.judge]` line and nothing else; tests 620 → 675, none broken. Results land in `evals/<subject>/results-grounding-<ts>.json`, which inherits `.gitignore`'s unanchored `results-*.json`, and carry the judge model/temperature/`reasoning_effort`/prompt hash, the host CLI version/model/argv/task prompt, the groundly commit, `context_k`, the arm, and the whole `manifest.graphrag` block — recorded even for the graph-less vector arm, because four indistinguishable results files once cost a full misdiagnosis (2026-08-09). **The eval package writes nothing to `progress.db`; the measured pipelines write their normal traces.** That distinction matters and an earlier draft got it wrong by claiming nothing was written at all. `ask()` writes one `traces` row per question and every host `search` writes one — reading those rows back *is* the mechanism, so a sweep does add ~96+ rows to the student's own study history. No boundary is crossed: `core/bundle.py` still imports nothing from `core/progress.py`, the new helpers are pure `SELECT`, and progress.db still never reaches an export. **No interchange change**: no manifest field, no `store.db` schema, no `format_version` event.

**Measured result: not yet run.** The harness is landed, verified and smoke-tested end-to-end against the live MCP server: one apd question, one `search` call, 8 chunks, 82,618 tokens, $0.114, 24.6 s, correct answer. The sweep needs only a configured `[providers.judge]` key — the host runs on an ordinary subscription login, no API key. This entry is updated with the numbers when it runs — until then the experiment is built, not answered.
