# Web agent switcher and headless topic mapping

Status — implementation design, 2026-11-27. Extends decisions 46 and 50 once implemented.

## Intent

A student can create a course map, write questions, or grade written answers from the page using an agent they already have. They choose a provider, model, and effort once, see the values beside the action, and repeat the action with one click. Practice tests drawn from the question bank require no agent choice.

In this design a provider is a supported local agent CLI. A run starts a fresh headless process using that CLI's existing login. Connected MCP clients continue to report their activity through the header. Their connections, ordering, and current activity have no bearing on where the page sends work. Open-chat handoff, queues, chat input, raw model IDs, and remote agent runtimes are outside this design.

## Approaches

- **Action plus visible switcher, with remembered choices.** This is the agreed design. A separate control shows the destination before the student commits and keeps repeat runs to one click. It requires sharing the current selection across views.
- **A required picker on every run.** This gives each action a deliberate configuration step, with the cost of interrupting every repeat run.
- **Sending to a connected session.** Herdr and Orca can target sessions they manage. Groundly observes MCP tool use but has no route back into an arbitrary connected chat. Adding session discovery and delivery would solve a different problem.

## Interaction

```text
[ Write questions ]   [ Codex · Model A · High ▾ ]

                       Provider     Codex       ▾
                       Model        Model A     ›
                       Effort       High        ▾
```

- Put the shared switcher beside **Create topic map**, **Write questions** (including the big-topic action), and **Grade now**. The controls can wrap onto two lines on small screens. Before setup the switcher says **Choose agent**. Clicking the main action before setup opens the same popover with a **Run** button and the pending action's scope. The first available provider is preselected in fixed order, Claude Code before Codex, with default model and effort.
- The provider row expands into named chips with a short, slower fan-out of roughly 200–240 ms. Use an instant transition for reduced motion. The chips are operable during the transition. With one available provider show its name without an expansion control.
- The model row opens a single-column list in the same popover. **Provider default** comes first, the current option has a check, and choosing a row returns to the summary. Keep the list scrollable on a small screen. Search can wait until the list warrants it.
- The effort row opens a compact checkmarked list and returns to the summary on selection. **Default** defers to the CLI. Offer explicit levels only when Groundly knows the resolved model supports them. If the student deliberately changes to a model that cannot use their current explicit effort, the picker visibly changes effort to **Default**. A previously saved pair invalidated by a catalog refresh instead needs the student's attention.
- Selection edits update the adjacent button immediately. Opening or closing the switcher alone never launches an agent. After the first accepted launch, the main action immediately sends the currently displayed selection. Outside first setup, selection changes need no **Run** button inside the picker. Use dialog/popover focus handling, one selected option per list, keyboard operation, Escape, focus return, and readable text labels alongside any icons.
- Keep one active selection across views in memory. On a successful start response, remember the active provider and the exact submitted model/effort for that provider in browser-local storage. A reload restores the last launched selection. Switching providers restores that provider's last launched pair or starts from defaults. A failed start leaves the prior stored values intact. Use defaults in memory if browser storage is unavailable and validate stored data when reading it. A desktop browser and a paired phone have independent preferences.
- If the last selected provider or model disappears, or a saved effort no longer applies, preserve the stale choice long enough to explain the problem and open the picker on the attempted action. Require a valid selection and an explicit **Run** for that pending action. If discovery temporarily cannot verify an explicit choice, offer a catalog refresh or let the student explicitly pick defaults for the same provider. Keep the saved pair until another launch is accepted. With no usable provider, show the existing host prompt fallback. On launch errors, name the provider and show the actionable cause in the page. A launch, sign-in, or model error never triggers another provider automatically.

## Discovery and requests

- Extend `GET /api/runs`, which the page already uses for availability and reconnection. Return launchable providers in stable order, with provider IDs, display names, and supported model entries, each with an ID, name and effort options. Retain the target, active snapshot and no-provider reason. A provider is launchable when Groundly has a verified integration for the installed CLI version and can resolve its executable using the serving process's `PATH`. Installation and account access are separate. Resolve to an executable path on the server and validate again before spawning. The browser sends provider/model/effort IDs, never executable paths or flags.
- Claude Code and Codex are the first target integrations on macOS and Linux. The existing Claude Code path remains usable with defaults even where a CLI version lacks an explicit selection flag. Start with documented Claude Code aliases and a conservative version-compatible effort matrix. For Codex, use the local CLI's documented [App Server model list](https://learn.chatgpt.com/docs/app-server#list-models-modellist) if that catalog matches the isolated runtime. Bound and cache discovery per executable/version for the server process, and run it off the request event loop. Keep the picker responsive when metadata is unavailable. An integration can offer provider defaults if it has verified a default launch, with an explicit unavailable state for the catalog. Do not infer that a saved explicit model was removed solely from a failed catalog lookup.
- Add `map` as a subject-scoped run with no topic id. Extend the existing strict start body with a provider ID and nullable model and effort. Null leaves the relevant override absent from argv or runtime configuration. Validate every explicit choice server-side against the same catalog used by the picker. A missing provider, stale choice, invalid request or pending run spawns no process. Include the launch selection in the start response and snapshots so an existing run keeps its original label across navigation or reconnects. Only label an effective model or effort separately if the CLI confirms it.

## Execution and topic mapping

- Reuse the current runner, one-active-run rule, cancellation, timeout, run strip and SSE stream. Keep the CLI-specific launch, tool-boundary checks and stream parsing behind the two integrations. Use fixed argv and fixed task templates with the validated subject ID and, for writing, its integer topic ID. Use the packaged skill and let the CLI handle its own subscription. All integrations use ephemeral mode so launch does not save a resumable session or a local run transcript. Groundly holds no key, constructs no model client and opens no direct model connection.
- Keep the current Claude Code startup isolation and checks when adding model/effort overrides. For Codex, prove that a supported build can run with only the intended Groundly MCP tools before enabling it in discovery. The proof must show that shell/file tools, other MCP servers, hooks, skills from user or project configuration, and unrestricted subagents cannot take part in the run, including before the first turn. Read-only shell access falls short of this boundary. Require an equivalent check on every launch. If no tested integration meets it, ship the Claude Code switcher and leave Codex out of discovery until the gap is solved.
- Show **Create topic map** on the existing **Indexed, no map yet** card, with **Copy prompt** available for the student's own MCP chat. Indexing material continues through its existing flow. A map run starts from `outline`, reads pages where needed, and submits through `submit_tree` with the packaged mapping skill. Its tool surface is `outline`, `get_page`, `search` and `submit_tree`, locked to the clicked subject. Its page-specific instructions skip the skill's interactive setup, indexing, remapping, and subagent steps. It cannot replace an existing map, index files, delete questions, or write questions. Retain the current outline contract and the APD-sized acceptance baseline. If an outline exceeds the host's limits, report the failure and offer the existing manual fallback.
- Check that the subject is indexed, has materials, and has no map before starting. Bind the subject and first-map condition at the map run's MCP boundary. Enforce the first-map condition in the existing tree write transaction to handle another client mapping the course after the launch check. Return a machine-readable conflict, leave the winning tree intact, and let the page open it. Preserve the existing tree gate for structure, topicality, and citations. Ordinary MCP mapping and remapping retain their existing semantics.
- Reuse the activity display for external map runs and use the page's run state for the page-triggered run. A successful gate write drives the topic map refresh, card move, and **Open topic map** affordance. A model final message alone does not establish that a map was written. On Stop, timeout, or host failure, refresh from storage so a map already committed remains visible. A run that ends without a committed tree leaves the card available for another attempt. Keep run selection, errors, and progress out of exports. Render host output as text.

## Acceptance

1. With two supported CLIs, the picker shows both independent of MCP clients. Missing executables and incompatible versions cannot be targeted. Under paired access, the destination is on the machine running Groundly.
2. First use lets the student confirm settings and launch. After a reload, the action launches once with the exact last-used configuration and no further prompt. Switching providers restores their independent model/effort choices. Browser storage failure still permits a run.
3. An unavailable or incompatible saved choice requires reselection. Both the picker and start route reject unsupported explicit values. The provider and selection on an accepted run stay fixed if the next selection changes.
4. Each shipped integration passes a local, version-specific isolation check without a model call. Fake CLIs cover accepted launches, mismatched startup, stream completion, sign-in failures, Stop, timeout, and single-run ownership. A real-provider smoke on a disposable subject confirms the supported version and installed login path before that integration ships.
5. The new action creates a topic tree through the existing relevance gate for the selected indexed subject and links to it. A concurrent external map cannot be overwritten. Rejections and a run with no accepted tree leave no partial tree. Normal mapping from MCP and practice test creation still work.
6. Keyboard, narrow-screen, and reduced-motion browser checks cover the first-run form, provider expansion, model list, and effort menu. The existing write and grade buttons still refresh question counts and verdicts after their runs.

The same implementation change updates the master decision register, student-mode acceptance contracts, architecture and privacy docs, and repository rules wherever they specify a Claude-only runner, forbid model selection, or put mapping exclusively in host chat. Decision 37's no-key and no-client requirements still apply.
