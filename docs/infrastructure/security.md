# Security & Privacy Model

Single-user, local-first: most of the archived iteration's threat model (multi-tenant isolation, sandbox escape reaching other students' data, upload abuse) dissolved with the server. What remains is small, specific, and real. Ordered by exposure.

## 1. Import — the trust boundary

A `.groundly` bundle is third-party content that will enter the student's prompts and filesystem.

**Controls:**
- **Zip-slip protection**: extraction rejects entries escaping the target directory (no absolute paths, no `..`); symlinks not extracted.
- **Manifest validation before anything is read**: format version supported, counts sane, subject title short and free of control or invisible characters, each `ocr.lang` one bare name (up to 32 letters, digits, `-` or `_`, starting with a letter); unknown schema versions refused (`PRAGMA user_version` check on the imported store.db). A language reaches the extraction worker as one argv item with no shell, and RapidOCR only looks it up in its model table, so an unsupported name fails that file as `extraction_failed`; `index --ocr-lang` applies the same check before saving.
- **Imported chunks are layer-3 data** — delimited, quoted, never instructions ([`../architecture/agents.md`](../architecture/agents.md)).
- Imported SQLite files are opened with the same schema checks as native ones; no code paths execute content from the bundle.
- **The topic tree is checked after extraction**: a bundle without the tree tables, with dangling references (`PRAGMA foreign_key_check`) or with a tree deeper than two levels is refused. `PRAGMA foreign_key_check` only covers keys a file declares, so explicit anti-joins also check `topic_citations.topic_id` and `chunk_id` and `topics.parent_id`. **The tree's cost is bounded**: more than 1000 topics, more than 5 citations on one topic, a title over 200 or a summary over 500 characters (or either not stored as text), or more than 64 MiB of cited chunk text refuses the bundle, so `tree()` cannot be made to allocate without limit. An SQLite error while reading a hostile schema is reported with its cause and the temporary import directory is removed. Imported titles and summaries are layer-3 text, shown by the page only as text (section 4).
- **The question bank is checked after the tree** (decision 44): references resolve by anti-join, no question sits on a topic with subtopics, and the question gate's structure and limits are repeated (kind, text types and lengths, option counts and the shape of the answer key, 1 to 5 citations, 200 questions per topic). Grounding is not repeated: import loads no model. A version-1 bundle is upgraded on its first open, and one already holding an object named like a question table is refused rather than half-upgraded.
- **The store's shape is checked after extraction**: a store with a view or trigger the shipped schema does not define (same name and body) refuses the bundle before any other check reads a table, because a view runs when it is read and can answer these checks with one thing and later reads with another, and a trigger can rewrite rows after they pass. Tables and indexes are then compared with the shipped schema too (an extra, changed or missing object refuses the bundle), so a generated column or a dropped index cannot make the bank checks or later reads arbitrarily slow. So does a material row whose `filename` is not one path component (not text, empty, `.`, `..`, or holding `/`, `\` or NUL), whose `sha256` is not 64 lowercase hex digits, whose `status` is unknown, whose `pages` is not a number or whose `error` is not text; a chunk whose `page` is not a number; and a `materials` table missing one of these columns.
- **Reject or escape, by field**: a field with a fixed shape is rejected at import, because anything outside that shape means a file edited outside Groundly. A filename also needs more than escaping: `groundly remove` deletes the file it names, so a row holding `../../victim` could delete a file outside the subject. Everything else is free text, including the other characters a filesystem allows in a filename: indexing stores a file's own name, and real documents and parser output can hold control bytes, so refusing them would refuse real bundles. Free text imports and is made inert where it is shown. Display stays defended for every field anyway, because stores imported before this check, the student's own filenames and parser output reach the same code, and `remove` and the page each require a stored file to resolve inside `materials/` for the same reason.
- **Terminal output is inert**: Rich's `escape` and `Text` stop markup but pass ESC, so the CLI prints values from a store, a bundle or the filesystem through one helper that replaces control characters (except tab), Unicode line separators and bidi overrides with U+FFFD. A subject title stays plain `Text`: it is validated on every load and can hold none of them. Rich's emoji codes are off. A character stdout cannot encode prints as `?` instead of crashing the verb; this changes the stream only, never what is stored.
- **One damaged subject costs only itself**: `groundly list` warns and skips a subject with a bad directory name or an unreadable manifest. `index`, `title`, `remove` and `export` name a damaged manifest and change nothing; `drop` still removes the subject. `list_subjects` skips a bad directory name and reports an unreadable store as zero counts plus an `error`: `store.connect`'s named cause for a missing store or a newer schema, otherwise a fixed message, because SQLite's own can quote object names a hostile store chose.
- **Legacy `graph/` entries are never extracted** (decision 37). Bundles built before the graph was dropped still carry parquet; the entries pass the zip-slip and allowlist gates and are then skipped, so no parquet or lancedb reader exists in Groundly at all.

## 2. Prompt injection via documents

The student's *own* lecture PDFs are as capable of carrying "ignore previous instructions" as an import. All retrieved content — chunks, subject titles, and the titles and summaries stored in a topic tree — is layer 3: instructions inside it are inert by construction of the immutable system layer.

## 3. Subprocess execution (verifier + coding challenges)

An idea, not planned (spec §3, coding challenges): the verifier would execute LLM-generated reference solutions for code questions. No subprocess runs generated code today; until it does, code questions are refused at the door. This is the student's own machine running code produced by the student's own chosen model — self-risk, but bounded anyway:

**Controls:** temp working directory, wall-clock timeout, output size cap, no shell interpolation of generated strings (argv exec). No network isolation is claimed — documenting that honestly beats pretending a sandbox exists. (The archived gVisor design existed because *our server* ran *other people's* code; that premise is gone.)

## 4. Local servers

`groundly mcp --http` (MCP over Streamable HTTP), `groundly serve` (the topic-tree page) and `groundly start` (both in one process, the page at `/` and MCP at `/mcp`; decision 45) bind **127.0.0.1 only** — no-auth is acceptable exactly and only on loopback. Neither takes a `--host`. stdio MCP has no network surface at all.

**The topic-tree page** (`groundly serve`) is a new local surface, and a hostile page in the student's browser can reach loopback. What it exposes: read routes over every subject's tree, question bank (without keys until a test is submitted), chunk text and stored PDFs, one write route that saves a submitted test to `progress.db` (decision 44), and two that start and stop a run of the student's own Claude Code (decision 46). Controls:
- **Host header check** (`TrustedHost`: `127.0.0.1`, `localhost`, `groundly.localhost`) against DNS rebinding, as `mcp --http` has. The list is fixed: `groundly.localhost` is a loopback-only name in browsers (they resolve `*.localhost` themselves), so it adds no name an attacker's DNS can point here; MCP clients are given `127.0.0.1` instead, since the OS resolver on some Linux setups forwards `*.localhost` upstream. The name list, and the write route's Origin check compares against whichever of the three the page was opened on. Under `start` the same list goes to FastMCP's own Host/Origin guard on `/mcp` (routed at that one path, so every page route keeps its 405), and the page's CSP stays on page responses only. Under `start` the page's origin also carries the MCP tools that write `store.db` (`submit_tree`, `submit_questions`, `remove_questions`): a cross-site page cannot reach them (a JSON POST needs a CORS preflight, which gets no CORS headers, and a foreign Origin gets 403), but script running on the page's own origin could. The text-only insertion and CSP below therefore guard the question bank and tree too, not only `progress.db`. The port is limited to 1–65535, and a busy or refused port is named by cause.
- **Three write routes, none to `store.db`**: `POST /api/subjects/{subject}/attempts` (a submitted test, to `progress.db`), `POST /api/subjects/{subject}/runs` and `POST /api/runs/stop` (start and stop a page run, decision 46) are the only routes that take a write method; every other route refuses POST/PUT/PATCH/DELETE (405). Each requires an `Origin` equal to the page's own (`{scheme}://{Host}`, so a cross-site form or a `null` origin gets 403) and `Content-Type: application/json` (415 otherwise, which also keeps it out of reach of a simple cross-site form post); the attempt route also requires a token of 8 to 64 `[A-Za-z0-9-]` characters and answers that name questions and options of this subject; any fault writes nothing and starts nothing. The page opens `store.db` only to read, and the test suite holds a connection and checks `PRAGMA data_version` is unchanged across a whole student test. The body is capped at 256 KiB before it is read, ids must fit SQLite's 64 bits, and `serve` ignores `X-Forwarded-*` headers so only the socket decides the scheme and host the Origin is compared with. A student can submit any question of the subject, so a key is hidden from a drawn test, not from the student. The one CSRF control is the pair "own Origin plus a JSON content type, with no CORS headers anywhere": adding CORS, another allowed host or a looser content-type check would open the write routes (and with them runs on the student's plan) and the key-bearing result route to any page in the browser. Opening a store through `connect()` sets WAL mode and upgrades a version-1 store by adding the empty question tables; neither writes a row. It loads no model.
- **Untrusted text**: titles, summaries, filenames and chunk text may come from an imported bundle. The page inserts them with `textContent` only (a test bans the HTML-inserting sinks), under a CSP on HTML responses (`default-src 'none'`, `script-src 'self'`, `style-src 'self'`, `img-src 'self'`, `frame-ancestors 'none'`; no inline script or style), with no external resource. The page's own script and stylesheet are served from `/static/`.
- **Files**: a PDF is addressed by material id, never by a path from the request; its stored name must resolve inside the subject's `materials/` directory (symlinks out, `..`, embedded NULs and non-PDF suffixes are refused), and it is served as `application/pdf` with `nosniff`. Other formats are never served raw — an HTML file from a bundle would otherwise run script on the page's origin — and show the cited chunk text instead.
- **Page runs** (decision 46): a page request can start an agent run on the student's plan. Guards: the loopback bind, the Host list, the page's own `Origin` and a JSON body (which forces a CORS preflight from any other origin), and one run at a time (`run_in_progress`). The body carries ids only (`{kind, topic_id}`); the prompt is a fixed template filled with the subject name and an integer topic id checked against the tree, so no title, summary, question or answer reaches it. The subject name is an identifier from a strict character set, quoted in the prompt, but an imported bundle may have chosen it (rename on import with `--as`). The run is exec'd from an argv list with no shell, stdin `/dev/null`, in its own process group (Stop and the page's shutdown send TERM, then KILL after 5 s, to it and its children) and one fixed directory under Groundly's home. Its tools are cut to Groundly's: no built-in tools (no files, shell or web), no user or project settings (no hooks, plugins, CLAUDE.md or other MCP servers), a per-flow allowlist (a write run cannot remove questions, re-map or grade; a grade run cannot write questions) and `dontAsk`, so anything else is denied, never prompted. The init event is checked before the first turn and any other tool or server kills the run (`isolation_failed`), so a `claude` build whose flags behave differently fails closed. The page shows steps built from tool names and counts and the final summary capped at 2000 characters, inserted as text; stream lines are read with a 1 MB cap. Windows is refused (`unsupported_platform`): an npm `claude` there is `claude.cmd`, which Python runs through `cmd.exe`.
- Residual: a PDF opens in the browser's own viewer on the page's origin, so a hostile PDF is a browser-viewer risk, not a Groundly one; the student's own materials carry the same risk anywhere.
- **Skill install**: `groundly skill install` and `uninstall` refuse a `SKILL.md` that is a symlink (dangling or not) at any of the three skills (`groundly-map`, `groundly-questions`, `groundly-grade`) or the old `groundly/` copy, with or without `--yes`, before writing anything, and name where it points; they never write through or unlink a link. A symlinked parent directory is allowed; one whose destination is gone is refused, naming it.

## 5. Privacy

- **Nothing leaves the machine** except model downloads from Hugging Face, plus RapidOCR models from modelscope.cn (sha256-pinned) only if a configured `--ocr-lang` resolves to a model not bundled in the rapidocr wheel. The exception the student starts: a page run (decision 46) is the student's own Claude Code, which sends their AI provider what a chat session would (course text, questions and, in a grade run, the written answers awaiting review); Groundly sends nothing itself.
- **The privacy boundary is a file**: `progress.db` — the student's submitted tests and answers (decision 44) — is never exported. The topic tree and question bank live in `store.db`, so they export with the bundle; the page writes an attempt to `progress.db` and nothing else (an older file gains its empty tables on first open; a page run writes through the MCP tools, decision 46), and `search` and the topic tree write nothing there. The `progress` and `review_answers` tools show the student's own host per-topic counts and the open answers awaiting review: the host is the reader they are meant for, and they leave the machine only as far as that host sends them. `store.db` exports carry the whole knowledge base including chunk text and original materials; the export UX says so plainly ("this bundle contains everything indexed in this subject, including its topic map").
- **Sharing = sharing course-material text.** Between enrolled students this is note-sharing; Groundly documents it rather than policing it (thesis acknowledges the copyright surface).
- **Debug logs are stderr-only, never a Groundly-written file.** `--debug` (on `index`/`search`/`mcp`) and `GROUNDLY_LOG_LEVEL` stream to stderr and nowhere else: a log file would be a new artifact holding query text and chunk ids that export code would then have to reason about, so there isn't one. Off by default at *every* level — `groundly/__init__.py` attaches a `NullHandler` so stdlib's `logging.lastResort` can't emit WARNING+ records on its own. inside the host-spawned `groundly mcp` process the switch is either `--debug` in the host's `args` or `GROUNDLY_LOG_LEVEL` in its `env`; every record goes to stderr precisely because that process speaks the MCP protocol over stdout.
- No telemetry, no accounts, no third-party trace storage (LangSmith was dropped for exactly this reason).

## Residual risks, named

- Imported text (a title, summary or chunk) may try to steer a host into calling `submit_tree`. A subject title reaches the host earliest, through `list_subjects`, even in a session about another course. The `list_subjects`, `outline` and `submit_tree` descriptions and the skills tell the host to treat course text as data, but nothing can prevent a host from obeying it; the gate still bounds what such a call can store, and it writes only the topic tree. Stored questions and reference answers (an imported bank is a stranger's) reach the host through `review_answers` and could try to steer it into inflated verdicts, which change only the student's own mastery, or into `remove_questions`, which cannot be undone and whose only guard is its description's "confirm with the student first"; answers already given stay in history either way. The tool and the grade skill name these fields as data, and the grade skill says they cannot ask for questions to be removed.
- Injection through a page run (decision 46): course text, imported bundles and student answers reach the run through tools, as in chat. No built-in tools, the per-flow allowlist, the gates and each skill's paragraph that this text is data bound it; an injected instruction can still skew questions or verdicts within the allowed tools, which is the chat session's risk, and the result page shows the cited page beside every answer. A grade run sends the student's written answers to the model, as "grade my test" in chat does; `progress.db` is still never exported. The page shows the run's summary as the model wrote it: the prompt forbids calling anything verified, but injected text could still make it say so. Every tool takes a `subject`, so nothing but the prompt keeps a run on its own subject.
- A malicious `.groundly` bundle with a crafted SQLite file targeting parser bugs — mitigated by schema checks, not eliminated.
- A malicious `.groundly` bundle sized as a zip bomb — declared uncompressed sizes are checked before anything is decompressed (manifest.json capped at 1 MB, bundle total at 20 GiB), relying on zipfile's own enforcement of each entry's declared size on read; a legitimately-huge bundle under that cap exceeding the student's free disk still fails, but at extraction with an OS error, not silently.
- Docling parsing a hostile PDF (from a merge-by-reindex of imported materials) — contained to the extraction subprocess (`extraction_failed`), not the app. One worker serves a run's files in turn (decision 48): a crash or timeout costs only the file in flight and the next file gets a fresh worker, but a parser exploit could reach the later files of the same run, all of them the student's own, under the same privileges.
- OCR rasterization on adversarial page geometries (a huge MediaBox rasterizes to multi-GB bitmaps) — bounded only by the extraction subprocess's wall-clock timeout, no memory cap; an OOM kill is contained to the child (`extraction_failed`) but the machine takes the memory pressure first. Standalone image inputs (decision 17) share this exact risk class — a huge-dimension or multi-frame raster decodes in the same subprocess, same timeout bound, no explicit pixel/frame cap. These bounds are now **user-tunable** (decision 18): `ingestion.timeout_seconds` and `ingestion.max_image_pixels` default to the shipped values but a user may raise (weaken) or lower (harden) them on their own machine, and an **opt-in** `ingestion.max_file_size_mb` rejects oversize inputs before they reach the extraction worker. The image-pixel cap is passed to the worker as an integer env var (`GROUNDLY_MAX_IMAGE_PIXELS`), not through the hostile-document channel.
- Generated code doing something hostile inside the timeout — accepted as self-risk on the student's own machine, stated in docs.
